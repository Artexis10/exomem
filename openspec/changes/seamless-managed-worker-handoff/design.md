## Context

See proposal.md for the production measurement. A read-only code map and an evidence-first reproduction (2026-09-13, disposable 446-file vault, real `FileWatcher`, scripts retained under the session scratch root as `lane-debug/scripts/{harness,exp4,exp5,exp6}.py`) established the mechanism:

- The public listener and accepted connections live in the supervisor; only the worker child is replaced, and the MCP transport is stateless, so there is no session to lose. The upgrade sequence is pause ingress, drain (30 s), stop the old worker, run the offline state migrator, spawn the new worker, poll `/health` and `/health/ready`, resume. The whole transition budget is 40 s and nobody serves between stop and ready.
- `/health/ready` reports `ready` from the tool surface, lease state and lexical admission only. Model preload and graph state never gate it, and the heavy background threads (graph drain, media, retrieval compute) start in-process at about the same moment traffic resumes.
- `freshness._external_pending` and `file_watcher._SELF_UPSERTS` are process-local. The new worker starts with an empty self-upsert table, so every inotify event it cannot attribute to itself (the old worker's last writes, the migrator, ordinary vault traffic) re-arms `external_pending`. `EpistemicGraphIndex._open_read_snapshot` consults that flag first and declines the predecessor probe, `_graph_sync_predecessor_state` reports `graph_sync_predecessor_unreadable`, and `upsert_after_write` collapses that into the same branch as a real lineage gap: a whole-vault rebuild. On a live vault the flag is continuously re-armed, so every write rebuilds. Measured: clean writes 0.17 s incremental with zero rebuilds; with the flag armed 3.5 to 4.0 s per write, every one a rebuild.
- `_join_registered_standalone` waits on `graph_sync.wait_for_registered` with no budget, so a caller that cannot carry a pending outcome blocks for the whole rebuild. MCP callers can carry pending and return fast, which matches the production acknowledgements; the one 314 s non-response was not reproduced and is not explained by mutation-boundary contention (a governed write during a rebuild completed in 0.32 s).
- Keyword recall during one rebuild degrades by about a third (p50 178 to 234 ms); what makes it permanent is back-to-back rebuilds, not one.
- The cold snapshot proof costs 0.66 s for 446 files, about 3 s at 2,000 notes, and adopts the previous snapshot; it never ran on the write path because the external-pending fence fails earlier.

## Goals / Non-Goals

Goals: a managed upgrade leaves the service usable within seconds; a write after a worker replacement takes the incremental graph path; no write ever waits unbounded on graph work; rebuild demand coalesces; the cold start of a replacement is paid while the old worker still serves.

Non-goals: session persistence (none is needed), changing the MCP transport, the OAuth authority, the public endpoint, write scope or compute mode, or the per-request recall stage budgets owned by `bound-connector-request-latency`.

## Decisions

### Phase 1: the rebuild loop is a dispatch defect and is fixed as one

**D1 External-pending fences reads, never governed writes.** `external_pending` exists so a read that requires a current projection can refuse rather than serve stale relations. A governed write does not require a current projection to compute its own predecessor: `_open_read_snapshot` applies the fence only to `require_current_projection=True` callers. For writes the predecessor probe always runs.

**D2 An unreadable predecessor is queued repair, not a lineage gap.** `upsert_after_write` routes `graph_sync_predecessor_unreadable` to the incremental path with the affected paths recorded as graph repair demand, returning `pending`. Only a proven lineage mismatch or an unusable snapshot (schema, registry, corrupt checkpoint) schedules a whole-vault rebuild. The two states stay distinct in the returned outcome so the alarm and the doctor can tell them apart.

A cold cache is the same judgement reached through a second door, found on the 0.83.1 deploy. `resolver_snapshot_unavailable` fires when this process holds no resident recall resolver for the checkpoint, and `recall_resolver_snapshot_at_checkpoint` refuses to build one on a miss by design (building from current disk would lose the pre-delta topology the bounded edge repair is proved against). Its disposition was `rebuild`, which enqueues nothing, so dispatch saw a deferral without queue coverage and registered the whole-vault pass anyway. It is now `defer`: everything needed to bound the damage is already proven when it fires -- the durable checkpoint matched, the acknowledgement was the predecessor, and the recall delta came back complete -- so the pass queues that delta, the sidecar still holds the stale resolver entries, and a later drain with a resolver resident re-runs the same pass and widens to the topology-affected sources itself. Dispatch reports `graph_repair_cold_resolver`, its own outcome for D2's reason. The eight remaining `rebuild` reasons are unreadable or self-inconsistent *stored* state, not cold caches, and stay whole-vault. The path-scoped external-pending fence is a third door to the same judgement and is answered the same way in D3: it sits ahead of the incremental pass, so it is not one of those reasons, but the set it describes is equally bounded and equally the queue's to own.

**A deferral never advances the lineage it did not publish.** The graph_sync acknowledgement is a statement about what was *projected*, not about what was promised, and advancing it on a queued receipt would make drift silent if the drain never landed: readers would see a current epoch over rows nobody had repaired. So a deferral withdraws the marker and leaves the acknowledgement where it was, and the cost is the one task 1.13 addresses -- the next write's predecessor probe sees a gap that is real but self-inflicted, and answers it with a whole-vault pass. The way to close that is to make the probe *prove* the gap is covered, not to weaken what the acknowledgement means.

**The coverage rule.** A predecessor probe that finds the acknowledgement *behind* this write's checkpoint treats the gap as covered when every generation it skipped is already on the durable graph repair queue, and as a proven divergence otherwise. Coverage is per generation because that is what the queue records: a canonical batch enqueues its own changed and created paths under the generation it commits, and every deferral route enqueues under the generation it was owed for, so a generation present in the queue has its whole path set queued -- the same claim an enqueue already had to make to report `queued` at all. Covered routes to the incremental path, which defers and queues this write's own paths and publishes nothing, so the acknowledgement is still never advanced on a promise; the outcome is `graph_repair_covered_gap`, and it claims durable per-path coverage alongside the other three. It is fail-closed on everything the artifact cannot show: a skipped generation with no receipts, a single receipt that cannot say which generation it owes, an acknowledgement that is level or ahead rather than behind, and an unscoped external mark -- an unknown affected set is the one thing a path-keyed queue cannot cover.

**Prerequisite: receipts carry their generation.** `graph_upserts` gains a nullable `graph_generation`, migrated in place, so an existing queue upgrades without losing work and every pre-upgrade row reads back as unknown and is never usable as coverage. A re-queue moves the claim forward to the newest known generation and never backwards, and an enqueue that does not know its generation does not erase one that did. The same field closes the staleness hole in the batch-coverage blessing: receipts count only when queued at or after the generation the deferral reports, because repair owed for bytes that have since been overwritten is not repair for what just changed.

**D3 External marks are path-scoped.** `_record_external_locked` records the affected paths; `external_pending` becomes "there are unrepaired external paths" and those paths drain through the existing bounded incremental repair. A write on one path is never fenced by an unrelated external edit. With path-scoped marks the process-local self-upsert table no longer needs seeding across a handoff: the worst case after replacement is a bounded list of paths to repair incrementally, and that is measured in the regression test rather than assumed.

A mark scopes the fence; it does not decide the repair. A write whose own paths are under a path-scoped mark still defers -- this process cannot trust its view of them -- but those paths are a bounded, known set, which is the definition of work the durable queue owns, so the write queues exactly them and reports `graph_repair_external_pending`. Returning a bare deferral instead made dispatch read it as a missing rebuild: measured at seven whole-vault passes across six writes when every write's own path carried a mark. The watcher's own repair of that mark is deliberately not treated as the coverage, because a dead or exhausted watcher would turn that assumption into silent debt; the drain converges the receipts through `drain_paths`, which does not pass this fence, and the refresh is idempotent if both land. Reads keep refusing until that repair lands, exactly as before. The watcher's fail-closed default -- a mark with no scope at all, raised when it cannot classify a fan-out incompleteness -- is excluded: it states that the affected set is unknown, so no set of paths the write could enqueue would be the repair, and that arm keeps the whole-vault pass.

**D4 Every join on graph work carries a budget.** `_join_registered_standalone` derives its wait from the request deadline when one exists and from a bounded default otherwise; past the budget the caller receives `pending` with the checkpoint it can poll, exactly as MCP callers do today. No caller can block for the duration of a rebuild.

**D5 Rebuild demand coalesces.** Demand arriving while a rebuild is in flight sets one follow-up mark; at most one further whole-vault pass runs after the current one, never one per write. The single-flight owner stays as it is.

**D6 Regression evidence is the reproduction.** Measured residue after D1 to D5: a fresh interpreter cannot derive a delta from a checkpoint another instance published, so its first write still pays one whole-vault pass (`recall_delta_incomplete`); every later write is incremental. D7 removes that pass by proving the snapshot in the standby before promotion. The `exp5.py external` shape becomes a test: a live watcher, one unattributed edit before each of ten writes, and the assertions are zero whole-vault rebuilds, incremental acknowledgement latency within a stated bound, and the repair queue draining to zero. A second test replays a real worker handoff through the supervisor harness and makes the same assertions for the first ten writes after promotion.

Adoption has to be reachable as well as recorded. `adopt_recall_origin` names a local generation as the foreign checkpoint's origin, but `recall_delta_since` bridges a checkpoint by replaying the retained history from that origin forward and refuses anything below its front -- and the history begins where this process's registry went live. A promoted worker's watcher re-seeds that registry on start-up, which resets the history to empty at a new generation while the adopted origin, held at the older one by the deliberate `min` that keeps a re-proof from retiring work the first origin still owes, survives it. Adoption therefore also seeds a zero-path history entry at the origin it has just declared usable. The entry satisfies the guard and contributes nothing to any delta, because the replay skips every entry at or below the origin, and the claim is backed by the proof the adoption already took: the caller established that the snapshot's sources match disk, which is why it succeeded. This does not widen `recall_delta_incomplete`, which keeps answering genuine `DELTA_HISTORY_LIMIT` overflow with a rebuild -- the floor is an ordinary history entry and is trimmed like one.

**Adoption runs on the unconditional start-up path.** It is not a cache, so no cache-preload policy may decide it.

**Adoption is admission-ordering, not warm-up tidiness.** Hoisting it out of the cache gate was necessary and not sufficient: on 0.84.1 it ran, and still ran too late. `warm_all` built the semantic corpus first -- 30-36 s on 4209 pages -- and governed writes are admitted the moment `semantic_corpus` is marked ready, so the first write of the replacement worker was admitted 36 s before the handoff. It had no delta origin, fell back on `recall_delta_incomplete`, and registered the whole-vault rebuild adoption exists to remove; that rebuild was still in flight when adoption finally ran, so the proof was taken against a sidecar being rewritten underneath it and declined. Two rules follow, and they are one decision stated at both ends. First, **the graph handoff runs immediately after the retrieval catalog and before the semantic corpus**, ahead of everything a writer waits on. Second, **the mutation admission gate waits for the graph handoff as well as the corpus**: `readiness` gains a `graph_handoff` component, and a write arriving before it settles is refused `MUTATION_WARMING` with the same retryable shape, the same `retry_after_ms` and the same `committed: false` the corpus refusal already has -- callers retry it without knowing which component held them. Reads are untouched.

The component is marked ready on every exit from the step, including the ones where nothing ran: it means "the delta origin is as good as this process will get it", which a declined or skipped adoption satisfies as much as a successful one. A component that could be skipped without being marked would hold every write until the whole warm, model preloads included, finished.

Nothing that exists to protect a *cache* may gate it. Not the resource mode (`mode=normal` is the default and leaves `preload_cpu_caches` False -- that is how 0.83.1 skipped it); not the corpus build (that is how 0.84.1 admitted a write ahead of it); and not `catalog_ready`, whose detached repair owner republishes the *lexical* catalogue while this step builds a process-local resolver and proves the *graph* sidecar -- different artifacts, so the collision that makes `warm_caches` wait does not apply. A proof taken against a moving projection declines and says which condition it declined on; a proof never taken costs the next write a whole vault. The one remaining gate is `EXOMEM_DISABLE_WARMUP`, kept deliberately because it is an explicit operator opt-out from warming at all rather than a default state the process reaches on its own; it is not set on the personal service.

**A decline says which condition declined it.** `snapshot_proof_declined` restated `adopted=False` and told an operator nothing: on 0.84.1 it took a hand-correlated service log across three minutes to establish that a concurrent whole-vault rebuild had been rewriting the sidecar. The cold proof now reports the arm that fired -- `recall_membership_unreadable`, `source_unparseable`, `indexed_membership_differs`/`indexed_sources_differ`, `resolver_topology_mismatch`, `projection_moved_during_proof`, `proof_raised` -- and the warm-up's adoption line carries it. The arms are enumerated from the source by test, so a new one has to name itself. The same applies to the lineage-gap probe, whose uncovered branch was silent: it now names the generations it could not prove covered, which is what distinguishes a lost best-effort enqueue from a real divergence without reading the queue by hand.

**The coverage convention is enumerated, not assumed.** The per-generation shortcut in D2 rests on a claim no probe can check: an enqueue that records generation G records G's *complete* path set. The generation-recording call sites are therefore enumerated from the source and each declares what set it claims, in the style of the unbounded-join declaration, so a new site recording a partial set fails loudly instead of inheriting the claim. One site records a deliberately partial set -- the adopted residue -- and is sound only because it records the *acknowledged* generation, which a gap probe never asks about. On the 0.83.1 deploy adoption and the recall resolver primer both sat inside `warm_caches`, which returns at its first gate when the resource mode does not preload CPU caches; the personal service runs `mode=normal`, where that gate is closed, so neither ran and warm complete listed only the retrieval catalog and the semantic corpus. `warm_graph_handoff` now runs both from `warm_all`, still after the admitted catalogue and the watcher's registry seed because `adopt_recall_origin` refuses a cold scope, and the gate keeps deciding only the disposable caches.

### Phase 2: the replacement warms as a standby, then is promoted

**D7 Standby before cutover.** The supervisor spawns the candidate beside the serving worker in standby: it binds its private socket, warms the lexical catalog, loads models when preload is allowed, opens the graph snapshot read-only and runs the cold proof, and reports a distinct `cutover` readiness. It takes no writer lease, publishes nothing, schedules no drain and owns no state. The old worker serves throughout. The standby warm budget is separate from the 40 s cutover budget and defaults to minutes; a standby that does not reach cutover-ready inside it is discarded with a recorded reason and the old worker keeps serving. The standby's snapshot proof is a direct call and does not go through `warm_caches`, so it is unaffected by the cache-preload policy for the same reason the start-up path now is. The standby needs no admission gate of its own: it takes no writer lease, so no governed write can reach it, and promotion acquires ownership, applies the residue the adoption owes and only then releases the activation that resumes ingress -- the ordering the `graph_handoff` component enforces on the cold start-up path is already structural here.

The standby's warm covers everything the write admission gate waits on, and the semantic corpus is one of those things. Building it is a process-local read: it walks and parses Markdown, resolves in memory and caches under a module lock, takes no mutation lock, writes no sidecar and publishes nothing, so a standby may do it beside a worker that still owns the vault. A serving worker writing underneath it only makes the built context stale for those pages, which the stat census the cache is captioned by repairs on first use; what the gate needs is that nobody pays the cold build, and that survives.

Promotion then hands the warm forward rather than repeating it. It records which readiness components this process completed and promotion either re-verified or cannot invalidate, and the promoted worker's own `warm_all` subtracts exactly those. It is a subtraction, not a second warm path: a cold start carries nothing and runs every step. `graph_handoff` is carried only on a `current` snapshot verdict -- the one case where re-adopting could not return a different answer -- so `advanced`, `unproven` and `rebuild-after-promotion` each leave it out and the handoff runs in full. `readiness.begin_warm` clears every event, so the carried components are re-marked synchronously, before the warm thread starts and therefore before any request can be served; marking them on the warm thread would reopen the window this exists to close. What remains after a carried promotion is the small residue: the retrieval catalog check, and any model the standby's preload policy did not load.

**D8 Promotion is short and ordered.** Cutover pauses ingress, drains, stops the old worker and proves its descendants exited, runs the offline migrator only when the target release declares a state migration (otherwise the step is recorded as skipped), promotes the standby (it acquires ownership, re-validates the snapshot it proved, applies the repair that adoption owes, and starts its schedulers), and resumes.

Re-validation is proportional to what could have changed. The migrator is the only writer between the two workers, and whether it runs is declared by the staged target, so: when it ran, the standby re-runs the whole source proof before promotion; when it did not, promotion re-compares the recall and graph-sync checkpoint pair, which is what a write by anyone else would move. A full source proof in the second case would add seconds to the one window this change exists to shorten, for a writer the sequence has already excluded. If the proof or the comparison fails, the standby rebuilds after promotion using the phase-1 coalesced path, and the handoff record says so.

Adoption's residue is applied at promotion, not during the warm. Proving a snapshot is a read, but enqueueing the repair it owes is scheduling a drain and withdrawing the availability marker is publishing graph state -- both belong to whoever owns the vault, and during the warm that is still the old worker. The standby therefore adopts with the residue returned rather than applied (`apply_residue=False`), carries it, and applies it once promotion is accepted. Making the checkpoint the delta origin is process-local, so deferring the two writes costs the adoption nothing.

**D9 Readiness names what it means.** `/health/ready` keeps `ready` for serving and adds a `cutover` component set: `lexical`, `embeddings` (when preload is allowed), `graph_snapshot`, `semantic_corpus`. The supervisor polls `cutover` for a standby and `ready` for a promoted worker. Operators see which component a candidate is waiting on. `semantic_corpus` is in the set because the write admission gate waits on it: a standby that reached cutover-ready without it would promote into a worker that refuses writes, which is a cutover that has moved an outage rather than removed one. It reports *settled* rather than *built*, the same distinction `warm_all` draws when it marks `graph_handoff` on every exit: a build that ran and failed is as good as this standby will get, and the promoted worker pays that same failing build whether it cut over or cold started, so holding every release for a defect the standby cannot fix would cost more than it prevents. A build that never ran is not settled, so a stalled standby is still discarded when its budget expires, and a failed build is never carried forward. The same block reports `carried_from_standby` after a promotion -- the components the promoted worker's warm is entitled to skip -- which is the first thing to read when a cutover is fast but the writes after it are not.

**D10 Rebuild leaves the request CPU -- withdrawn from this change.** The proposal was that a whole-vault rebuild run in a bounded child process at reduced priority, with the in-process path as a fallback and the readiness surface reporting which ran. It was admitted on a measured need -- one rebuild cost recall about a third on a 446-file vault -- and deliberately scheduled last, to be re-measured once phase 1 had removed the back-to-back case. Task 2.4 did that (2026-09-14, 4,000-note fixture) and the answer moved the decision out of this change: recall during a single rebuild stays inside its ceiling, so what remains is a cost question, not a correctness one, and phase 1 plus phase 2 have taken rebuilds down to at most one per handoff and soon zero. It is carried to Open questions with that measurement as its entry condition rather than built here.

**D11 Streams retry through promotion.** The ingress reattachment retries the upstream `GET` with backoff inside the cutover budget instead of closing the stream on the first non-success, so a long-lived client's stream survives a promotion it never noticed.

**D12 Queued vocabulary recovery drains after activation.** Once the graph projection is current, the activation sequence drains the bounded recovery queue in the background rather than waiting for an explicit review call.

**D13 Preload is an operator setting for the personal service.** `EXOMEM_PRELOAD_MODELS=1` goes into the personal service environment; it is a deployment step, not a code default, because the shared machine configuration is also read by the second instance.

## Risks / Trade-offs

- Narrowing the external-pending fence could let a write compute a predecessor against a stale projection → the predecessor is derived from the checkpoint lineage, not from the projection, and the regression test asserts drift stays zero across external edits.
- Path-scoped marks change what "current" means for reads → reads still refuse while any external path is unrepaired; only the write path changes.
- A standby doubles memory briefly (two workers, two model copies) → bounded by the warm budget; the standby is discarded, not the serving worker, when the host cannot afford it.
- Skipping the migrator is a correctness risk → it is skipped only when the target release declares no migration; the declaration is part of the staged target and is verified by the existing target check.
- **Adoption is what a replacement worker's first write depends on, and a
  mid-traffic handoff does not guarantee it.** A write that defers withdraws the
  availability marker, and the background repair may not have republished it
  before the old worker stops, so the promoted process inherits a fenced sidecar
  and one whose recorded bytes are behind the vault for the deferred paths.
  While adoption ran the public-reader proof it refused exactly those vaults --
  in 23 ms -- and the first write then paid a whole-vault pass which, under
  continuous writes, cannot stabilize (Class C, three attempts, 10-12 s) and
  which a standalone caller has to join. Measured over four runs: adoption
  succeeded once and gave six writes at 0.50-0.82 s with zero joins; the run
  whose predecessor left the sidecar fenced failed adoption and paid 7.2 s on
  its first write and 11.0 s later. The discriminator is adoption, not lineage
  age. Adoption therefore proves through a maintenance read and tolerates a
  bounded residue (one drain pass, `graph_drain.DRAIN_LIMIT`, which makes a residue of N paths cost ⌈N/64⌉ drain passes -- a bound asserted from the constant, not measured against a production residue): it adopts the
  checkpoint, queues exactly the unrepaired paths, and leaves the marker
  withdrawn so reads still refuse until that repair lands. An unbounded residue
  or a structurally unusable sidecar still pays the whole-vault pass.
- **What the fence door cost, and what closing it leaves.** One mechanism in the chain below is now closed: the path-scoped fence returned a bare deferral, so dispatch answered `incremental_refresh_deferred_without_queue_coverage` and scheduled the vault. Probed with a live watcher and a mark on each write's own path at dispatch, that was seven whole-vault passes across six writes with acknowledgements of 1.3-2.0 s; with the fence queueing its own paths it is zero from that door and 0.2-0.6 s. What remains is a second-order effect of deferring at all: a deferral publishes nothing, so until the drain converges the queued paths the graph's acknowledgement stays one generation behind and the next write's predecessor probe reports a proven gap through the gate D2 keeps. With the graph drain daemon running between writes -- its production cadence, within a second of the write that queued the debt -- that door contributed one pass across six writes, and it was `graph_sync_predecessor_present_at_genesis` on the first write of a freshly built fixture. Without a drain between writes it contributed six. Whether a deferral should also advance the lineage it did not publish is a separate decision and is not taken here -- it is task 1.13, and the answer recorded there is no.

  The drain mitigation is rate-dependent, and the bound should be read as such: it holds while writes arrive slower than the drain cadence, about one per second. A batch ingest at several writes per second sees each write dispatch before the previous one's debt has drained, so the predecessor gap returns per write. It stays bounded -- by the join budget and by rebuild coalescing, so it is a slower ingest rather than a rebuild per write -- and task 1.13 closes it: measured on that shape, six whole-vault registrations across six writes with acknowledgements of 1.32-1.37 s become zero, at 0.18-0.20 s.
- **A withdrawal with an empty queue had nobody to earn it back.** Every route that withdraws the availability marker pairs it with durable repair, and the drain republishes while repairing those paths; the last withdrawal, landing after the final drain, had no later drain with work to republish it. Reads then refuse indefinitely and `graph_drift` -- which reads through a public snapshot the marker gates -- audits an intact sidecar as missing or drifted. Measured as `graph_state=current queue_remaining=0 drift=1` on the 0.84.1 evidence run of the concurrency harness, and as `available` False with an empty queue in the phase-1c review probe. The drain now republishes when the queue owes nothing, on the same source-bytes proof adoption uses and with no residue tolerated, and it never advances the graph_sync acknowledgement: this restores readability of what was already projected. Attribution: all six phase-1b commits pass the harness locally, and `99207f5b` differs from the last of them only by a version bump, so this is an intermittent race that phase 1b did not introduce -- it reproduced once in eleven local harness runs. The deterministic guard is therefore a unit test, not the harness.
- **What that does not close.** With a live watcher repairing unattributed edits
  while governed writes continue, the two writers advance the graph lineage
  independently, and a governed write whose predecessor has genuinely moved
  registers a whole-vault rebuild through the proven gate D2 keeps
  (`reason=graph_sync_predecessor_mismatch`, or `..._present_at_genesis` on a
  freshly built vault). Under that same write traffic the rebuild cannot
  stabilize -- `attempts=3 elapsed_ms=11934.1 class=C cause=the recall
  projection identity moved across the pass` -- and a standalone library caller,
  which has no envelope to carry `pending`, joins it (bounded at 15 s), reports
  the re-raised `GraphProjectionMoved` as `failed`, and then joins the successor
  that publishes. The write itself always succeeds: its canonical bytes are
  durable before any of this. Observed in one write of six across runs, moving
  between writes as the lineage race does, and independent of whether adoption
  succeeded (seen with residue 0 and with residue 3). Every mechanism in that
  chain predates this change and two are deliberate (the proven gate, the
  stabilization contract); closing it means either letting a standalone caller
  carry `pending` -- which ten governance and deletion-lineage tests currently
  forbid -- or making a rebuild that lost a race to concurrent writes report
  something other than `failed`. Both are their own decisions.
- **What the 0.83.1 deploy measured, and what it changed.** The first release carrying phase 1 still rebuilt the whole vault twice on the personal service, and its first three governed writes acknowledged in 164.8 s, 46.7 s and 46.7 s. None of it was the dispatch defect phase 1 removed: `external_pending` was False on both rebuild lines, so D1 and D3 held. Four separate causes, each a door phase 1 did not model. (1) Adoption never ran, because it sat behind the cache-preload gate a `mode=normal` service leaves closed. (2) With no resident resolver the incremental pass bailed on `resolver_snapshot_unavailable`, whose `rebuild` disposition queues nothing, so dispatch reported `incremental_refresh_deferred_without_queue_coverage` and scheduled the vault. (3) The acknowledgement time was not graph work at all: no join ran, and the mutation boundary was released 49 s before the third write returned -- write 1 was 32.7 s of semantic corpus, 22.8 s of lazy embedding-model load and 93.6 s of cold embedding-matrix load (rows=72488, cached_gen=-1), while writes 2 and 3 each left ~32 s attributable to nothing but a 14.3 s `index.upsert_after_write` and a lexical `VAULT_LOCK_NESTED` deferral with no completion line. (4) The watcher's seed-time graph validation met the first write holding `semantic_existing_edit_commit` for 10.6 s, was refused `MUTATION_BUSY` by its one-shot `suspend_reads()`, and aborted -- leaving the graph unreadable with no persisted barrier, which is the state the drain then rebuilt from. Phase 1b fixes (1), (2) and (4), and instruments (3) so the next deploy attributes what is left rather than inferring it.
- **What the 0.84.1 deploy measured: adoption ran, and was admitted around.** The release carrying phase 1b/1c adopted nothing on the personal service, and the reason was ordering rather than the cache gate 0.83.1 died on. `warm complete` shows the semantic corpus at 30-36 s (4209 pages) and the graph handoff after it; the admission gate waits on `semantic_corpus`, so the first governed write was admitted at `04:37:11` with no adopted lineage, fell back on `recall_delta_incomplete` and registered a whole-vault rebuild for `generation=2978`. That rebuild was still running at `04:37:47.973` when adoption ran, and did not finish until `04:39:55.225` with `outcome=failed`; adoption's proof was therefore taken against a sidecar a concurrent rebuild was rewriting and returned `snapshot_proof_declined`. Which proof arm actually fired is not determinable from that log -- the generic reason is exactly the gap the named reasons close, and the next deploy reports it. Two doors are closed here: the handoff now runs before the corpus, and the gate that already refuses on the corpus refuses on the handoff. The residual risk is a *slower* first write rather than a wrong one -- a caller retries a `MUTATION_WARMING` for the seconds adoption costs instead of paying a whole-vault rebuild measured in minutes -- and the refusal is the retryable shape callers already handle. A declined adoption is not held against: the component is marked settled either way, so a vault that genuinely cannot be adopted warms at today's speed and pays today's rebuild.
- **The covered-gap proof was stored where a later enqueue could erase it.** Reviewed at 79ef13b9, the batch-ingest test failed 5/5 on the reviewer's host and 3/5 under a reproduced CPU load here, while the same shape WITH a drain between writes passed. The cause is neither a lost nor a late enqueue: the debt is queued strictly before the canonical bytes are replaced, so a committed checkpoint already implied its debt was written. It is that `graph_upserts` is keyed by rel_path and carries ONE generation column, so a re-queue of the same path moves it forward (`max(new, old)`) -- correct for a queue, because that row does still owe the newer repair, and fatal for a ledger. Traced under load: the receipts held `{2, 3, 4, 5}` before a governed write and `{6}` after it, because the running watcher re-queued those same paths at its own checkpoint; the next write's probe then read a proven divergence over generations whose repair was fully queued. The proof therefore moved to its own append-only per-generation record, written in the same transaction as the receipts and before the write acknowledges, which nothing overwrites and the drain does not consume. Clearing the whole queue clears it too, because a proof that outlived the queue it describes would bless a gap nothing is converging.
- **A hand-listed coverage allowlist that had drifted.** Both live tests named the dispatch outcomes that count as queued coverage as a literal set, and both omitted `graph_repair_cold_resolver` -- one of the five `index_sync._GRAPH_COVERAGE_CODES`, and exactly as covered as the three they did name. A run whose recall resolver went cold at dispatch therefore failed on a correct outcome (1 in 10 under load). Making the covered-gap door succeed more often routes more writes down the incremental path where that arm lives, so the fix above surfaced it rather than caused it. The tests now derive the set from the module that declares it, which keeps them asserting the contract -- this write's repair is durably queued -- instead of which doors happened to fire the day they were written.
- **A premise check that a third party could break on timing.** The same test asserted its rate shape indirectly, as "an unattributed edit is still outstanding at the end". That measures the WATCHER's catch-up rather than the test's own rate, and under load the watcher legitimately retires every mark before the loop ends -- two runs in ten, with the write path behaving perfectly. The premise is now asserted from the test's own evidence: nothing drains between the writes, and the covered-gap door only fires when a write dispatched with its acknowledgement genuinely behind its checkpoint, so counting those writes states the rate shape directly.
- **Two design gaps the 1.15 instrumentation found and did NOT fix.** They belong to write-path latency work, not to this change, which is measurement only. (1) *The edit-path advisory re-encodes the whole note on every append.* `edit` hands `corpus_aware.detect_contradictions` the entire body, which chunks and encodes it to find overlap candidates — so an append to a long page pays an encode proportional to the page, not to the append. Measured on 0.84.1 as an `embeddings.encode` of 15.6 s with `count=1` sitting entirely outside `index.embeddings` on one write, and 8.5 s of 30.4 s outside it on the next. The deferred surface already does the right thing and reuses the vectors the embedding pass published; the synchronous one does not. (2) *The derived drain re-enters the mutation boundary once per item.* One busy window produced 758 `mutation_lock` events — `deferred-index-store` 400, `refs-store` 246, `gate` 62, `embeddings-store` 20 — because `derived_drain.drain_once` dispatches one claimed `(batch, component)` pair per iteration and each reopens its store. That is a background thread, not the request, so it does not sit inside a write's own span window; what it does do is dominate the log (see below) and pay a boundary acquisition per item.
- **What instrumentation could not reach, and why it is said rather than skipped.** Two parts of the 1.15 brief could not be delivered as specified. The per-item boundary entries cannot become one span in a call's ledger row: `call_spans` is keyed off the MCP call token, and the drain that produces them runs on a background thread that never had one, so a span there would record nothing. The spans added instead cover the same stores where they ARE entered in-request. And the leaf-coverage guarantee is asserted at a floor rather than at 90%: on the test fixture one governed write over one path completes in 70-200 ms and varies by about a third run to run, so the same 20-40 ms of fixed cost lands in a different span each time. The guarantee that is stable, and that is what the 0.84.1 defect actually needs, is that every step inside the window is *named*; that is pinned step by step, with the ratio as a backstop.
- **The oracle that admitted the door 1.13 closed.** The per-write rebuild assertions were relaxed to `sum(...) <= 1` for a real reason -- the canonical batch's debt enqueue is best-effort by construction -- but `graph_sync_predecessor_mismatch` allowlisted unconditionally would have passed a 1.13 regression producing one mismatch rebuild in six. So the reason is still admitted, but no longer unconditionally: the probe names the generations it could not prove covered, and the tests read those generations back out of the durable record before letting the rebuild pass. A rebuild is admitted only once that read shows the debt really was never recorded. Absence is monotone across the window: the generations named are strictly older than the write's own checkpoint, and nothing records debt for a generation older than the one it is owed for.
- **What the first standby-sequence upgrade measured: the cutover worked, and the process it handed back did not.** 0.84.1 to 0.85.0 on 2026-09-14, the first upgrade run by the 0.85.0 supervisor. The standby warmed beside the serving worker from 10:21:36 to 10:22:33 -- adoption `adopted=True residue=0` at +37 s, the bge preload at +43 s -- promotion took 46.8 ms and re-proved `snapshot=current` with `residue_applied=0`, the migration was skipped `declared_none`, and the supervisor recorded `unavailable_ms=1672.9`. An observed client on an unbroken TCP connection saw exactly one slow request at 1.635 s across 245 samples, against the 19.4 s and 18.9 s the two cold sequences before it cost. D7 through D11 held end to end. Then the promoted worker ran an ordinary `warm_all` and repeated, in the same process, the warm its own standby had just finished: a second `graph snapshot adoption adopted=True residue=0` at 10:23:03, `semantic corpus context built pages=4271 build_ms=8516.1 cached=True` at 10:23:16, and `warm complete` reporting `graph_snapshot 19450.5` and `semantic_corpus 9935.2`. A governed write arriving at 10:23:0x was refused `MUTATION_WARMING warming_component=semantic_corpus`, and writes stayed refused for about thirty seconds. A 1.6 s unavailable window that hands back a worker which refuses writes for thirty has moved the outage, not removed it -- which is task 2.8, and is why `semantic_corpus` joins the cutover set and the carried warm exists. Measured after, on the handoff harness in a fresh interpreter: from promotion to the moment the admission gate's own predicate clears for both components, 545.9 ms before the carry and 0.4 ms after -- and the 0.4 ms is the synchronous re-mark, not a wait. The residual risk is the inverse: a carried component that promotion could not actually vouch for would admit a write into a process with stale state, so the carry is conditioned on what promotion re-verified and `graph_handoff` is carried only on a `current` verdict.
- **The first write after that promotion still rebuilt, through a different door.** Same upgrade, 10:24:49. Two clean adoptions and a watcher that reported `startup graph validation admitted a coherent graph` at 10:23:38, and the first governed write nonetheless fell back `recall_delta_incomplete` with `external_pending=False` and registered a whole-vault rebuild at generation 3075, taking 124 s; the second and third writes were incremental at 61 s and 51 s. Not unknown scope and not the dispatch defect: a cold origin. The adoption named an origin the delta history could not reach, because the watcher's registry seed had reset that history to a later generation while the adopted origin stayed behind it. It self-heals on the next write, which is why it reads as noise in a log and costs a whole vault in practice. Task 1.16 seeds the floor; the bound it must not erode is that genuine `DELTA_HISTORY_LIMIT` overflow keeps rebuilding, which a trimmed floor preserves by construction.
- **Phase 2 does not take effect until the launcher is maintained.** The supervisor runs from the launcher venv, which on the personal service was still 0.80.0 while the worker had moved on. An ordinary worker upgrade never touches it, so the standby sequence stayed dormant through two releases that contained it; the 0.84.1 to 0.85.0 upgrade above is the first one where the supervisor itself was new enough to run it. Anyone reading the unavailable-window numbers has to know which supervisor produced them, and any operator expecting a seamless upgrade has to run the documented launcher maintenance first. This is a deployment prerequisite, not a code default, for the same reason D13 is.
- **Recall during one rebuild, re-measured at production size: inside the ceiling, and that is the bound that governs.** Task 2.4 asked whether phase 1 had made D10 unnecessary. On a 4,000-note dense fixture (the personal vault is 4,271 pages), recall during ONE whole-vault rebuild goes from p50 7.9 ms to 18.7 ms and 8.2 ms to 20.7 ms -- 2.4x to 2.5x, and up to 4.6x at p95 -- all of it an order of magnitude inside the 300 ms p50 ceiling. The quiet phases either side reproduce each other (7.9 ms before, 8.1 ms after), so the middle is the rebuild and not drift.
  The ratio is worse than the "about a third" measured on the 446-file vault in the Context section, and the honest reading of the two together is that the ratio grows with corpus size. But a ratio is not a bound. The bound a user experiences is the recall ceiling, and recall stays well inside it, so the finding closes 2.4 rather than escalating it. The third probe query, at 2.3 s, sits outside the ceiling even when quiet -- that is a synthetic vault where one query matches nearly everything, not a rebuild cost, and reading it as one would be reading the fixture rather than the system.
  So D10 leaves this change. Rebuilds are now at most one per handoff and heading to zero, which turns the child-process rebuild from a correctness fix into a cost question with its own blast radius; it is carried to Open questions with this measurement as its entry condition.
- **`_assert_incremental_latency` is for a series of writes, never one.** It takes a median, and a median over one sample is that sample, so applying it to a single write converts a series-shaped budget into a per-request timing assertion -- the same premise class that produced the covered-gap and worker-replacement flakes recorded above. It reached CI once more this round: the first write after a promotion acknowledged in 1.14 s on a loaded runner and failed the 1.0 s median bound, on a write that was admitted and incremental exactly as the change intends. The guarantee that test actually makes is structural -- the write is admitted with no `MUTATION_WARMING`, reports an outcome claiming durable queue coverage, registers zero thread-attributed whole-vault rebuilds, and the promoted worker's warm names what it carried and logs no second adoption -- and each of those is now asserted directly. The latency signal it keeps is the 40 s transition budget the whole cutover is measured against, which is a contract rather than a guess. The helper now refuses fewer than three samples, and a test pins that refusal, so the next call of this shape fails at the call rather than in a CI run.
- **Two harness errors this measurement had to correct, recorded so the next one does not repeat them.** (1) *Sample at a request rate, not in a loop.* A tight sampling loop starves the thing it is observing: the rebuild's own wall went from 22.0 s quiet to 97.1 s, so the first run was measuring a sampler fighting a rebuild for one GIL rather than a user's query meeting one. Paced at four requests a second the wall was 67.8 s and the per-query numbers were stable. (2) *Report per query, never pooled.* The three probe queries cost 2.3 s, 8 ms and 8 ms on this fixture, so every pooled percentile reports which query it happened to land on -- a pooled p50 of 8 ms beside a pooled p95 of 2298 ms is one bimodal fixture, not a tail. Per-query medians made the signal legible: the degradation is uniform at 2.4x to 2.5x across cheap and expensive queries alike, which is what an in-process CPU-bound rebuild looks like from the request path.
- The 314 s non-response remains unexplained → D4 removes the only unbounded join found; the acknowledgement path is instrumented (ledger spans already exist for recall) so a recurrence names its stage.

## Migration Plan

Phase 1 is additive on the write path and deploys through the ordinary managed upgrade; the very upgrade that deploys it still pays today's cost once. Phase 2 changes the supervisor sequence; the first upgrade under it runs the old sequence (the running supervisor is the old code) and later ones run the new one. Rollback of either phase is a normal downgrade; no state format changes.

## Open questions

- Whether the 30 s stop-to-ready gap can also shrink by keeping the old worker serving reads during promotion. Not in this change; it needs the writer-lease design.
- **Move a whole-vault rebuild off the request CPU** (formerly D10, withdrawn from this change after task 2.4). A rebuild would run in a bounded child process at reduced priority, writing the sidecar and returning for the worker to publish under the existing single-flight owner, with the in-process path kept as a fallback and the readiness surface reporting which one ran. Entry condition, from the 2026-09-14 measurement: recall during a single rebuild costs 2.4x to 2.5x at p50 and up to 4.6x at p95, and stays inside the 300 ms p50 ceiling at 4,000 notes -- so this is worth doing when the ratio, which grows with corpus size, puts a real vault's ordinary queries near that ceiling during a rebuild, or when rebuilds stop being rare. Both are measurable rather than arguable, and neither is true today: phase 1 and phase 2 leave at most one rebuild per handoff and are heading to zero. Re-measure before opening it, with the harness corrections recorded in Risks above.
