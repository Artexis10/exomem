## Purpose

Distribute current Exomem Cloud to Claude and OpenAI from one portable operating contract, with reproducible packages and observable cross-surface acceptance.

## ADDED Requirements

### Requirement: One canonical behavioural core
Cloud provider packages SHALL generate their Skills and workflow resources from the generic shipped scaffold. Provider adapters MUST NOT fork recall, activation, capture, governance or mutation behaviour. Public artifacts SHALL contain only generic repository inputs.

#### Scenario: Provider parity
- **WHEN** both Cloud packages are generated
- **THEN** corresponding Skills and reference resources are byte-identical to the canonical payload and each other
- **AND** a missing or modified resource fails the package check

### Requirement: Current Cloud runtime identity
Packages SHALL target the current Cloud MCP resource and `product-cloud` capabilities, deriving their Exomem version from the source release. Alpha profiles and their release controls MUST NOT become Cloud runtime authority. Self-hosted Claude Code SHALL retain its separate configurable endpoint and identity.

#### Scenario: Latest Exomem packaging
- **WHEN** the source runtime version or canonical contract changes
- **THEN** regenerated package identity and reproducibility metadata change together
- **AND** historical alpha artifacts and self-hosted connection configuration remain separate

### Requirement: First-class activation and bootstrap
The canonical core SHALL establish live engagement and capabilities through bootstrap, activate absent context for substantive turns using the raw turn, preserve continuity, resolve ambiguity and avoid duplicate activation. Unsupported tools SHALL be governed by live capabilities, never invoked because another surface exposes them.

#### Scenario: Context and capability fidelity
- **WHEN** a fresh Cloud conversation needs durable context
- **THEN** the client obtains live bootstrap and calls activate_context with the raw turn before filling remaining retrieval gaps
- **AND** it refrains from unavailable media or transfer operations

### Requirement: Canonical profile-aware activation hooks
Supported local hook surfaces SHALL use release-owned retrieval, capture and continuation behaviour with explicit client and profile-local state. The installer SHALL support direct working-set injection and native-MCP delegation as separately observable modes. Native-MCP mode MUST NOT access provider credentials, an external hook transport or an implicit local vault. Working-set transport failure SHALL request native-MCP activation without claiming an injected packet. Existing default installation behaviour SHALL remain compatible.

#### Scenario: Remote MCP context activation
- **WHEN** a supported profile is installed in native-MCP mode
- **THEN** its canonical prompt hook requests bootstrap when necessary and one raw-turn activate_context through its admitted Exomem MCP
- **AND** its hook makes no external HTTP or local-vault CLI call

#### Scenario: MCP activation cadence and transport policy
- **WHEN** a second session or short referential resume needs activation inside reminder cooldowns
- **THEN** its activation instruction is not suppressed and forbids duplicate calls for current already-held context
- **AND** retrieval and capture make no external requests or service-credential reads in native-MCP mode, including episode and candidate-coverage checks

#### Scenario: Profile-bound current capture and continuation
- **WHEN** a named Codex profile executes its hooks
- **THEN** the canonical capture parser recognizes stable Codex messages and hook state remains local to that profile
- **AND** unsupported lifecycle events are not invented

### Requirement: Native provider packaging
The Claude bundle SHALL support Chat, Cowork and Code with a fixed remote MCP URL and complete resources. The public OpenAI archive SHALL use the portable root manifest and MCP schemas and SHALL exclude private app bindings, including bindings in compatibility manifests. Both packages SHALL contain valid identity, legal/support metadata, contained assets and safe deterministic archives.

#### Scenario: Public package validation
- **WHEN** public archives are checked
- **THEN** validators reject drift, missing resources, unsafe paths, private app bindings or invalid transport declarations

### Requirement: Shared behavioural evaluation
One versioned corpus SHALL define expected observable behaviour for all provider surfaces. Evaluation SHALL inspect actual tool calls, arguments, responses, citations and independent mutation readbacks. Unit observations or connection-only evidence MUST NOT count as native acceptance.

#### Scenario: Fabricated capture claim fails
- **WHEN** an observation claims durable capture without a successful write and independent readback
- **THEN** evaluation fails even if the answer claims success

### Requirement: Cross-surface readiness
Readiness SHALL require native install, authorization, current capability/contract identity, cited recall, durable capture and fresh-conversation recall on Claude Chat, Cowork, Code, ChatGPT and Codex. Cross-provider evidence SHALL show the same store and saved content. Missing, failed, stale or mismatched evidence SHALL produce a nonzero readiness result identifying the gap.

Native observations SHALL bind retained original exports and inspected projections by digest, conversation identity, actual user turns and installed package identity. Self-declared native/pass flags SHALL NOT establish acceptance. Capture readbacks SHALL use a different conversation, the returned memory reference and hidden synthetic content marker; fresh recall prompts SHALL NOT supply the expected answer.

#### Scenario: Partial acceptance stays partial
- **WHEN** package tests pass but one required native surface lacks evidence
- **THEN** readiness remains false and identifies that surface

### Requirement: Directory submission fidelity
Directory materials SHALL derive supported cases and identity from the shared release, use accessible legal/support URLs and actual demo evidence, and keep reviewer credentials out of public files. Submission, approval and publication SHALL be reported separately.

#### Scenario: Submission is not publication
- **WHEN** both providers accept submissions for review
- **THEN** the recorded outcome is submitted and never automatically approved or public
