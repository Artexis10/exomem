## Context

The baseline is Exomem 0.99.0. `server.py` serves `product-cloud` from the normal command registry minus `CLOUD_SURFACE_EXCLUSIONS`. This is independent of alpha profiles v1-v5. The public protected-resource document currently identifies `https://exomem.substratesystems.io/mcp` and the existing Substrate OAuth issuer. The generic scaffold already teaches bootstrap, activation, continuity, governed writes and live engagement. Existing `package_skills` builds the core and standalone workflow resources from that scaffold.

## Goals / Non-Goals

Deliver generated native packages, one shared behavioural evaluator, native acceptance and directory submissions. Keep the self-hosted Claude Code identity separate. Do not revive the retired alpha promotion/cohort/deployment-lock machinery, add a new auth backend, or implement import/media features withheld by Cloud. No runtime-side reasoning model is introduced.

## Decisions

1. Add `cloud_plugins.py` and `scripts/cloud-plugin.py` as current Cloud targets beside the historical alpha renderer. Reuse generic skill payload construction from `package_skills`; expose a public payload helper instead of duplicating its file selection. All canonical skill and reference bytes are identical across Claude, OpenAI and generic self-hosted packaging. Capability restrictions are taught in the canonical scaffold, not injected provider prose.
2. Use `plugins/cloud/definition.json` for public product identity, URLs and publisher, deriving the runtime/package version from checked-out `pyproject.toml`. Generate `plugins/cloud/generated/claude` and `openai`. Generate release JSON recording version, skill contract, corpus digest, profile and complete file digests. This is reproducibility evidence, not a serving/promotion protocol. Preserve legacy package bytes.
3. Claude uses `.claude-plugin/plugin.json` and `.mcp.json`; OpenAI uses Agent Plugins 1.0 root `plugin.json` and `mcp.json`, with an optional matching `.codex-plugin/plugin.json`. No private app dependency belongs in public archives. Include README, license and actual referenced icons. Public metadata explicitly says Exomem Cloud and describes supported behaviour.
4. Add one generic corpus under `plugins/cloud/evals/`. Each case describes setup, natural-language prompt, required/forbidden calls, argument checks and observable results. Native runners export actual traces into a common format. The evaluator checks observed calls and successful results, citation and synthetic content markers, capture readbacks and continuity. It rejects missing observations, errors, claimed writes without independent readbacks, mismatched package/runtime identity and stale evidence. Evaluator unit fixtures prove checking only and cannot count as native acceptance. Native acceptance additionally retains source exports and their SHA-256 digests, actual user turns, distinct conversation identities, installed package identity and observed bootstrap identity. Normalized observations must resolve to those exports; a self-declared `native` or `pass` flag proves nothing. Capture/readback binds the returned memory reference and unique synthetic content marker; fresh-chat prompts cannot contain the expected answer. Reject relabelled unit traces, reused conversations and explicit save prompts presented as proactive capture. This is inspectable evidence, not a new runtime attestation service.
5. A `readiness` command requires five separate native surfaces (Claude Chat, Cowork, Code, ChatGPT, Codex), each with clean install/OAuth and the same current Cloud resource, plus cross-provider readback. JSON reports missing/failed/blocked items and exits nonzero until complete. Submission metadata is generated from the same corpus: five positive and three negative cases, legal/support URLs, publisher, country targeting, commerce declaration and actual demo URL when supplied. Do not create invented proof, credentials, video links or attestations.
6. Public packaging and local tests proceed without portal access. Complete portal preparation only after native acceptance. The operator enters secure reviewer access and legal attestations in the intended publisher account. Submit both Claude listings and the one universal OpenAI listing; publication follows approval in a separate milestone.
7. Do not inherit the historical EEA/US allowlist: target all platform-supported countries without an additional product restriction. OpenAI expresses this as `publication.countries: []`. Launch as an existing-account connection, not in-plugin commerce. Current OpenAI plugin policy prohibits digital subscription sales, upgrade prompts and checkout links; existing paid-account access is permitted. Keep the existing website billing flow separate. Source: [OpenAI submission metadata](https://developers.openai.com/plugins/deploy/submission), [commerce policy](https://developers.openai.com/plugins/plugin-guidelines), audited 2026-09-30.

## Risks / Trade-offs

- Provider manifests change independently: validate against current primary docs and schemas and record adapter versions; behavioural files remain shared.
- Imported connector tools alone do not prove skill activation: native traces must include unprompted activation and capture in ordinary conversation, then fresh-chat readback.
- A scaffold workflow can describe excluded Cloud tools: add one canonical capability guard and test that clients receive the live exclusion list; do not silently claim complete media/import workflows.
- Client UI and publisher sessions may be unavailable: continue package/evaluator work, report exact access dependency, and leave native/submission tasks open.
- Other sessions are delivering runtime changes: rebase only this task tree on current main and regenerate all version/digest-bound outputs before final verification.

## Migration Plan

Create a new Cloud distribution with separate stable `exomem-cloud` identity. Preserve existing self-hosted/alpha identities and auth state. Merge the reviewed batch through CI, publish generated packages by the ordinary repository release process and check the actual deployed Cloud runtime before native acceptance. Roll back package selection to the previous verified release; runtime rollback follows the existing Cloud image/backup procedure. No new runtime database migration is required.
