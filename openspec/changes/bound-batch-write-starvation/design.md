## Context

A media backfill (16-path `reprocess` calls and hour-long audio jobs) made foreground writes slow or refused on a personal service. The service log showed 176 commit-generation advances in 40 minutes, 78% from media. Each advance sets off corpus-sized derived work in the serving process, so request threads got little CPU. A separate worker process is out of scope. This design contains the load inside the one process.

## Decisions

### The graph checkpoint failed for two reasons, and both are fixed

1. The fan-out of a media publication was told that no page was created. A reprocess creates a prior-extraction page, so the checkpoint named a created page that the fan-out did not. The incremental refresh refused the checkpoint (`checkpoint_created_paths_mismatch`) and queued the paths instead. The fan-out now receives the checkpoint's created paths.
2. The graph floor and its checkpoint were published in a second boundary take. When that take was refused, the floor stayed ahead of the checkpoint. The next writer saw a recoverable epoch, wrote a full-scope checkpoint and rebuilt the whole graph (lineage gap). The epoch is now published inside the commit's own hold, so no refusable take sits between the floor and its checkpoint.

### One batch is one hold, one advance and one fan-out

The supervisor drains up to `BATCH_RESULT_LIMIT` durable results. It stages each result inside one hold, commits all their sidecar writes in one `batch_atomic_write`, and publishes the epoch in the same hold. The fan-out runs once after the hold, for all pages. A failure rolls the whole batch back and leaves the results in `media_job_results`. The supervisor then bisects exactly the results of that batch, one half per pass, and re-reads them by key, so a queue that reorders or outgrows the read window cannot hide the failing result. A half that publishes leaves the failing result in the other half; a half that fails narrows to that half. A result that stands alone and fails is set aside: it stays out of the batches of the other results, so the others publish meanwhile. It retries alone in the first pass that has no other batch to publish, and in any pass once it has waited `MAX_DEFER_SECONDS`, so a transient failure recovers on the next pass when nothing else waits, and otherwise at the first pass after it has waited `MAX_DEFER_SECONDS`, so a busy queue cannot starve it. One set-aside result retries per pass, the one that has waited longest. It is forgotten when its own result ends. Isolating a failing result costs one failed hold a pass, never a burst of holds. A result that fails while it is staged names itself and stays pending; the others commit in the same hold. Setting it aside would turn a transient refusal during staging into a long wait, and the batch is not failed. A refused boundary ran nothing, so the batch stays pending, whole, for the next pass. A result whose write paths overlap an earlier result in the batch waits for the next batch.

### Publication waits for a quiet foreground gap

The supervisor reuses `foreground_activity.idle_seconds`, the signal that the dreamer and the review pass use, and invents no second one. A batch needs `QUIET_GAP_SECONDS` of quiet, and `MIN_BATCH_SPACING_SECONDS` since the last hold. Every hold that ran sets the spacing, because every hold advances the commit generation, even one that staged nothing or rolled back. The progress floor lets a result publish without a quiet gap once `MAX_DEFER_SECONDS` have passed, so continuous traffic cannot hold publication back forever. The floor counts from the later of the oldest result and the last hold, so a result that never stages opens it once per floor. While foreground writes stay busy the supervisor reads the queue once per floor, and polls only the clock and the activity signal between. The wait is durable and visible: the results stay in the job store, and `process_media status` reports their count and the age of the oldest. The count is unknown (`null`) when the read fails, and zero only when the results table does not exist.

All budgets live in `media_publication.py`. The supervisor's gate and its batch publisher read that module; the status read reports the queue they act on and uses no budget.

### A reprocess request queues without advancing the commit generation

Planning a reprocess path reads the whole file for its hash, and for an evicted original it hydrates the file first. That work never runs under the boundary, because one large file would stall every foreground write. A path whose transcript is complete then commits only a row in the machine-local job store. The request takes that row's hold with `projection_guard`, which holds the boundary and leaves the commit generation alone, so six paths advance it zero times where each used to advance it twice. A path that needs a sidecar commit takes the ordinary advancing hold, and its fan-out runs after the hold. A non-advancing hold never writes canonical content. If the media runtime becomes unavailable between the plan and the hold, the path must also write a blocked page, so it changes nothing under that hold and runs again with the advancing one; its page, job and result row then show the blocked state, as they did before this change.

The zero-advance claim holds in a file-mode vault. In a store-mode vault the sidecar step of a path runs on the store thread, whose bookkeeping hold takes its own advancing guard (`projector._holding_boundary`), so a path advances the generation once there, where it advanced twice before.

### An upload commit moves its bytes before it takes the boundary

On 2026-11-21 an evidence-lane upload commit (`upload_preserve`) held the boundary 59 times in six and a half hours, 2,838 s in all (p50 43 s, longest 165 s), about 86% of every hold in that window, while keyed saves were refused `MUTATION_BUSY`. The door wrapped the whole `preserve_stream` in the boundary, so a file of about 900 MB was copied and hashed into a spool, copied and fsynced again into the batch workspace (or into the original pool), and then fanned out, all inside one hold. On a disposable vault, idle, a 150 MB upload held for 6 s (copy 2.5 s, stage copy 2.3 s, fan-out 0.4 s, rest 0.9 s); the first two grow with size and the other two do not.

Each upload door now copies, hashes and fsyncs the bytes once, before the boundary, into a private stage on the vault's own filesystem. A pooled vault stages into the pool with `original_pool.prepare`, which already stages every byte and publishes by rename. An ordinary vault stages into one reserved directory under the managed root, held by an owner lock. Inside the boundary the commit re-plans against current state, adopts the stage into its batch workspace by rename, rechecks the stage's identity on the held descriptor and rebinds the generation witness (the rename moves the file's change time, and an unbound witness would hash the file again), installs, and writes pages and indexes. Nothing inside the boundary scales with the payload.

What stays inside the boundary because it reads current state: destination spelling and admission, destination taken (including a pooled filing), companion absent, raw-protection naming, the format state, the index and log `expected_hash` guards, and the create-only checks. What moves out because it reads bytes: the spool copy, the workspace copy, pool staging and confirmation, the artifact identity hash and the provenance hash that follows an upload. A container whose plan reads the whole archive (`document_containers.plan`) stays inside for now and is a named residual.

A stage is not canonical. A crash after staging leaves only a stage; a sweep at serving activation removes a stage only when its owner is proven gone, never by age alone, and leaves in doubt what it cannot prove. A stage whose bytes change before adoption fails the batch's identity check and publishes nothing; the session stays retryable. A rename install needs the stage on the vault's filesystem; when it is not (`EXDEV`) the commit falls back to today's copy under the boundary and names that fallback in the holder status. A rename is used, not a hardlink, because provenance reads refuse a file with more than one link.

`upload_reconcile` hashes the whole binary under the boundary; it now passes `commit_guard`, as startup reconcile does, so the hash runs outside it.

Not in this slice: routing evidence commits through `invoke_command` so the fast durable acknowledgement defers the fan-out (0.4 s warm, 1.5 s cold). It is its own slice and its own risk surface (the replay store).

## Risks

- A media result can become visible a few minutes later than before under continuous foreground writes. The progress floor bounds the delay, and the status field shows it.
- A publication hold lasts up to `BATCH_HOLD_SECONDS` plus the staging of one result, because the time cap is checked between results, plus the batch commit itself. The commit grows with the number of results staged, which the read size `BATCH_RESULT_LIMIT` bounds. A reprocess queueing hold covers one job row, with no planning inside it. A foreground write that waits for either is inside its latency budget.
- A stage on a pooled vault holds the pool pin for as long as the upload takes to stage, where the pin used to be held only inside the hold. The media custody owner agrees the pin lifetime.
- A stage that a crash leaves is bytes that no page names. The sweep bounds the listing and reports what it cannot prove orphaned, rather than deleting it.
