## Decisions

Use the stored intake principal and the verified request principal. Bind a personal connector's receipt to the same issuer, owner account, client, login generation, and audience. Bind an offline OAuth login by its verified refresh family. Access-token rotation changes its access identifier and leaves its family intact. Other credentials keep their access identifier. Before release, verify that login through its authoritative session store. The stale-grace cache can sustain the connection during an issuer outage. It cannot release a receipt with unpublished data. A newly signed-in client can make new saves. The local administrative command recovers the old login's receipts.

If a retry has a recognised original identity and belongs to an older login, keep its execution claim. Withhold its reference, payload, and outcome from the new login. Asking for the reference through review and asking for a missing reference give the same result. If an index recognises a retry but the service cannot read its stored owner, withhold the result and preserve the claim. An unreadable store at startup with no known claim keeps the existing contention-path fallback. A future pre-dispatch acceptance path must establish custody before executing.

The hosted OAuth connector keeps its implicit retry identity on refresh. The managed local issuer provisions long-lived access credentials and has no refresh endpoint. Retain its existing implicit namespace. Qualify any future local refresh flow with a stable retry identity before enabling it.

Keep the existing local administrative recovery command. This phase restricts signed personal connector receipts and leaves the existing policy for receipts from unbound ingresses in place. A signed connector cannot use that legacy policy to look up an unbound receipt. An unbound request cannot read a receipt with a signed origin. Treat a partially bound personal connector as unable to release a receipt. Cloud issuer revocation and legacy owner credential separation require their own ingress proof.

Decide access before reading arguments or projecting outcomes. Use one verified scope for lists, counts, queue positions, and notice consumption. Report position only when the scope is complete and it fits the first list page. Name up to that page's limit of failures per reply and keep later failures available for the next eligible reply. Use the same verified request login in final release checks. An origin that the worker cannot independently verify is outside future pre-dispatch acceptance.

Use the existing stored principal record for lookup. A legacy receipt contains an access identifier without its refresh family. Inspect its ownership fields before opening its payload. For a verified refresh family, consult the issuer once for that comparison, even when the receipt is missing. List, notice and retry queries use the current family and access identifier as indexed scopes. If a newer receipt belongs to another login, reuse the original execution claim and search the caller's indexed scopes. Earlier receipts with an old access identifier and no stored family remain available by exact reference or local recovery. The list indicates that older saves may need exact lookup.

Index list and notice work by receipt scope. Verify the query on a large failed history under one login and under unrelated logins. Keep aggregate counts from scanning retained history on the request path. On a legacy store without scope summaries, exact lookup remains available. The idle drainer prepares the indexes with a short lock wait and a bounded retry interval. Until then, list and counts report unavailable.

Recheck signed receipt authority after the MCP and REST transports verify the final host boundary. Keep an earlier failure unnamed until that check succeeds. If another transaction holds the intake store when the reply is ready, leave the notice for a later save.

The proof exercises public receipt polling, retry, and notice paths with two verified clients and two logins under one owner, a token refresh, and a revoked login. It verifies the retained administrative recovery command against an older receipt.
