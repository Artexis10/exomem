## 3. Readers

- [ ] 3.1 Point every reader of page bytes or derived rows at the store in store mode: lexical, graph, reference and semantic-unit readers, page reads, `find`'s parse cache (keyed by store revision), governance frontmatter reads and the registry overlay loaders.
  - Done: in store mode a request that reads the vault retires the file-built lexical catalogue for its own reads (`lexstore.catalogue_retired_scope`). `find` keyword, browse, category and kind filters, unit and mixed results and the vault scope answer from the store's pages through the scan rung, and `ask_memory` reads through them. The managed browse and keyword readers and the managed admission contract have no store form, so a store-mode request bypasses them.
  - Done: the by-path reference lookup that `ask_memory` makes for each hit reads the store's identity rows, which `derive.py` writes with the page. Governance egress reads a stored page's bytes and identity from the store, and so do membership, the physical-path resolution, the decision receipt's content hash and the managed-governed-path rule.
  - Left: the graph readers (`relations`, `relation_of`, `graph_context`, the typed graph lane, the graph step of `ask_memory`) and the reference readers other than the by-path lookup still read the file-built `.graph.sqlite` and `.refs.sqlite`. The store holds their rows (`derive.py` writes the graph and identity tables), but each reader proves readiness through the sidecar's publication and lineage state. A store form needs a readiness projection over the store revision.
  - Left: the inbound-link index (`vault._build_inbound_index`) walks the disk and keys its cache on the freshness registry, so a page that only the store holds is missing from it. It needs the store corpus and a store-revision key.
  - Left: a Records or Planning layer and a page outside the Knowledge Base folder are files that the store does not own, so the scan rung reads them from disk and no derived row of the store covers them (D3). The reference reader has the same gap: `_refs_from_connection` checks for a duplicate id over the identity rows of unowned pages too, and the store holds none. Give those rows an owner before a SQL repoint.
  - Left: the working-set readers behind `recall_context` still call the file-built lexical catalogue: `working_set_runtime` (the task-context lexical search), and `working_set` (the semantic-unit search, the task-context text search and the eligibility metadata read). They need the same store form as `find`.
  - Left: two sites of `readiness.runtime_managed()` have no store form. `find_candidates` uses it to defer the cold load of the embedding matrix, which is the vector reader and not in this task. `lexstore._hand_off_stranded_scopes` uses it to hand stranded file-catalogue scopes to the repair owner; store mode retires that catalogue, so the store-mode lexical read does not reach it. Neither is proven in store mode.
  - Left: the scan rung reads every page of the corpus, so its cost grows with the page count (see 3.2). Reading the store's derived `pages`, `meta`, `fts`, `tri` and unit rows with SQL would remove that cost. It needs the readiness rows and the owner of unowned rows above.
- [ ] 3.2 Remove freshness witnesses, mtime checks and sync-on-first-use repair from the store-mode read path.
  - Done: the store-mode `find` and `ask_memory` readers schedule no repair and read no stored page's file or its stat, for the owner and for an external caller under an active policy. The corpus walk drops a stored page's projected file before it stats it. Governance egress decides a stored page under its store key, so a projection that is a link to another path, in the vault or outside it, neither leaks a page in a `paths` scope nor costs a stat. The container-claim check skips the probe of a stored page's file. `tests/test_vault_store_readers.py` proves each, on a vault whose projections are poisoned or deleted, by counting stat calls on stored page paths and repair requests.
  - Done: one store snapshot per recall tool call. `op_find` and `op_ask_memory` open it (`read.request_snapshot`), and the parse cache, the corpus walk, admission, the reference lookup and the hit annotation join it. The test counts snapshots at the tool entry for a 20-page and a 60-page vault, for the owner and for an external caller under an active policy: one in each case.
  - Left: `document_containers._remembered_unclaimed` keeps a file-mode read's answer (the page makes no container claim) by the projection's file version. A store-mode request in the same process would stat that file and trust the answer over the stored bytes. Only a process that reads a vault in file mode and then migrates it reaches this. Migration runs offline, so a service cannot, and no product migrate path calls `clear_unclaimed_notes`: a long-lived reader kept open across an offline migration (such as the TUI) keeps stale answers until it restarts.
  - Latency budget for store-mode `find`, from one measurement of one fixture (a store-mode vault with N pages committed through `write.commit`; `find` hybrid, keyword and browse, and `ask_memory`; 5 repeats; median of the cold repeat after `find.clear_cache()` and of the warm repeat). Before the work, N=500: hybrid cold 7022 ms (14.0 ms a page), warm 2171 ms; `ask_memory` cold 9377 ms, warm 2217 ms; keyword and browse refused with the typed warming outcome. After, N=500: hybrid cold 538 ms (1.07 ms a page), warm 141 ms; keyword cold 881 ms, warm 154 ms; browse cold 514 ms, warm 72 ms; `ask_memory` cold 1039 ms, warm 350 ms. After, N=2000: hybrid cold 1619 ms (0.81 ms a page), warm 503 ms; keyword cold 2849 ms; browse cold 2050 ms; `ask_memory` cold 3004 ms, warm 887 ms. The runs shared a busy 16-core host, so each figure is a median on a loaded machine.
  - Budget: cold at most 2 ms a page for `find` and 2.5 ms a page for `ask_memory`, warm at most 0.5 ms a page for `find` and 0.8 ms a page for `ask_memory`, and a snapshot count that does not grow with the page count. The budget is linear because the scan rung reads every page. By the 2000-page run, a 10,000-page vault would take 8 to 14 s cold for `find` (an unverified projection), which no interactive request can accept. The SQL repoint in 3.1 must land before the gate opens.
  - Left: the graph and reference readers and the inbound-link index keep their freshness witnesses and sync-on-first-use repair in store mode until 3.1 repoints them.
  - Left: the policy files under `_Governance` stay disk-resident (a reserved family that the store does not own), so loading the policy still reads files.
