## Context

The capture contract already treats conclusions, recurring entities, executed methods, intent, and observed outcomes as durable stepping stones, but it has no explicit class for stable personal or longitudinal context stated casually. That omission makes the active agent mistake conversational tone for low durability. The fix spans bootstrap, portable, and Hosted carriers, but it must preserve the no-nudge architecture: deterministic carriers can remind, while only the active conversation agent judges meaning and invokes existing governed leaves.

Hosted v1-v4 candidates are immutable and currently resolve some shared skills. Changing those shared bytes would invalidate historical packages, so changed Hosted behavior needs a self-contained v5 candidate rather than regeneration of old releases. This change is the release owner for one shared v5 candidate containing both the baseline doctrine and the generated-artifact adoption doctrine; the sibling artifact change participates in that same unrendered candidate and does not mint a second v5.

## Goals / Non-Goals

**Goals:**

- Define a narrow, testable predicate for stable preferences, recurring habits, historical baselines, and durable affiliations.
- Route eligible context to a resolved Entity, a concise compiled observation, or an existing Records collection according to meaning.
- Carry the same predicate through every active agent surface without adding a semantic service or background LLM.
- Measure false positives with synthetic positive/negative twins and mutation tests.
- Release changed Hosted behavior without changing v1-v4 bytes or identities.

**Non-Goals:**

- Capturing fleeting preferences, one-off activities, isolated trivia, tentative claims, or every measurement.
- Replacing the separately shipped executed-method, Planning, or Records predicates.
- Creating collections, schemas, or Entities merely because a baseline was mentioned.
- Amending or claiming a comparative no-nudge benchmark result before its governed amendment prerequisites are met.

## Decisions

### D1. Eligibility requires both durability and reusable comparison value

A fact is eligible only when it is stable or recurrent and useful for later comparison, interpretation, or decisions. Both discriminators are required. This catches casually expressed long-term context without treating tone, proper nouns, or ordinary detail as capture commands.

Alternative considered: enumerate phrases such as “favourite” or “always.” Rejected because phrasing is language-specific and cannot establish durability or usefulness by itself.

### D2. Routing follows semantic ownership

A stable facet or affiliation of a uniquely resolved Entity is attached to that Entity. Other eligible baselines become one concise compiled observation. Records are used only for a compatible observed event or measurement. Ambiguity never causes implicit Entity or collection creation.

Alternative considered: store every baseline as a Record. Rejected because enduring context is not necessarily an event and this would fragment canonical knowledge.

### D3. Executed methods remain a distinct capture class

The executed-method predicate continues to require actual execution, a reported informative outcome, and a reusable method or lesson. A baseline does not need an executed method, while an unreusable one-off result cannot pass through the baseline path.

### D4. Carriers remind; the active agent decides

Bootstrap, scaffold, workflow skill, documentation, and the structural capture hook carry the same compact doctrine. The hook remains a language-agnostic reminder and never classifies prose or calls a semantic model.

### D5. One owner co-delivers all pending Hosted doctrine in v5

V5 owns copies of every skill it ships, including the core skill, and binds one candidate-scoped behavior-fixture digest into compatibility, package, lock, and promotion evidence. The v5 source, fixture, render, lock, archive, and promotion tasks have one implementation-lane owner under this change. That owner MUST integrate and pass both this change's baseline cases and `preserve-adopted-generated-artifacts` adoption/draft/handoff cases before the first v5 render, lock, or promotion. The artifact change may add doctrine and fixtures to the still-unlocked candidate but cannot independently render, lock, roll back, or promote v5. V1-v4 retain their legacy resolution and must reproduce byte-for-byte.

Before the first v5 lock, a failed doctrine can be removed from the candidate and the combined candidate rebuilt. After v5 promotion, its source, fixture, package, lock, archive, and promotion identity are immutable; any correction ships as v6 rather than removing or mutating v5.

Alternative considered: edit the shared Hosted skill and regenerate all candidates. Rejected because it would rewrite immutable historical identities.

## Risks / Trade-offs

- [Carrier wording drifts] -> Validate semantic elements across all carriers and generated copies rather than relying on sentence equality.
- [The predicate becomes too permissive] -> Require both discriminators, publish paired negatives, and run mutants that remove either boundary.
- [Compact bootstrap grows] -> Trim duplicated prose and retain the existing budget; do not raise the cap without a separate decision.
- [Hosted history changes accidentally] -> Hash and check every v1-v4 source/generated artifact before accepting v5.
- [A new fixture is mistaken for benchmark evidence] -> Keep it an ordinary synthetic behavior fixture unless the benchmark amendment process explicitly admits it.
- [Two changes race on one Hosted candidate] -> Give one lane ownership of all v5 files and require both changes' doctrine and fixture gates before the first render.

## Migration Plan

1. Land red-first fixture and carrier-parity tests.
2. Update generic portable carriers and regenerate only their defined derived copies.
3. Integrate the generated-artifact adoption doctrine and fixtures into the same candidate-owned v5 skills before rendering or locking.
4. Render one v5 package/evidence set and promote only after baseline, artifact, and historical immutability gates pass.

Before first lock, rollback removes the failed doctrine from the unpromoted v5 candidate and rebuilds it. After promotion, rollback selects an older candidate for new sessions but never removes or mutates v5; a semantic correction requires v6. Existing stored notes and v1-v4 packages need no migration.
