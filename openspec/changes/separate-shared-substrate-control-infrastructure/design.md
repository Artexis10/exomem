# Design

## Context

See proposal.md for motivation. The deployed control host remains in Exomem's `infra/terraform/foundation`: `hcloud_server.control`, `hcloud_primary_ip.control_db`, `hcloud_firewall.control` and the database DNS record. Its private attachment references the foundation subnet and its creation references the foundation administrator key. `infra/ansible/site.yml` runs base and PostgreSQL roles against `control_nodes`; the shared base role also configures fleet nodes. Dedicated pgBackRest resources remain in the separate durability root. Provider locks pin Terraform 1.15.8, hcloud 1.66.0 and Cloudflare 5.22.0.

PR1513 changed the intended host label to `substrate-control-01`; its live rename is pending. Coordinate with that delivery owner rather than folding a rename or Kimai migration into state extraction. The verified access failure is a stale guest SSH allowlist, with sshd running; complete managed SSH acceptance before host inventory or recovery work.

## Goals / Non-Goals

**Goals:** Establish `substrate-systems/substrate-infra` and fixed shared foundation/durability workspaces; transfer existing management; preserve operating dependencies and recovery; make Exomem a consumer.

**Non-Goals:** Hetzner project transfer, server replacement or reboot, changing database endpoints or credentials, moving product migrations, applying the pending rename, Kimai migration, tenant-fleet changes or Cloud releases. Provider transfer requires an independently designed maintenance/connectivity plan: Hetzner requires detaching assigned Primary IPs before moving a server between projects.

## Decisions

1. **Extract ownership before relocating infrastructure.** Keep the provider project, subnet and attached addresses. This separates product ownership without a network cutover. Combining provider transfer would introduce downtime and private-route changes into a management-only operation.
2. **Preserve two lifecycle domains.** Use explicitly configured local/state-only HCP workspaces `substrate-control-foundation` and `substrate-control-durability`, inheriting lock/history/no-auto-apply/no-global-state-sharing safeguards. Do not combine database compute and backup credentials into one state.
3. **Use declarative forget/import, not recreation.** Inventory exact state addresses and provider IDs, including dedicated pgBackRest resources, then generate reviewed source `removed` blocks with `destroy=false` and target import declarations. Preserve existing addresses where practical. Do not copy raw state into Git or initialise a target workspace implicitly. Test the transition on disposable resources before production.
   Extend the existing saved-plan inspector with an explicit, manifest-bound handover mode accepting only the selected forget/import operations and IDs, rejecting creates, updates, deletes and replacements. Its current ordinary mode rejects `forget` and permits creates/updates, so it cannot be reused unchanged.
4. **Keep external dependencies explicit.** The first split leaves the shared network/subnet and foundation SSH-key resource under their current owner. The target consumes exact non-secret IDs and validates the dependency; it never manages a second network or key. Exomem consumes a versioned shared-control contract carrying its stable endpoint/TLS expectations rather than reading target state. Provider identifiers and environment values remain operator inputs, not hardcoded public examples.
5. **Separate host and application authority.** The target owns OS hardening, PostgreSQL/PgBouncer operation, certificate renewal and backup scheduling. Existing application migration/grant ownership remains with the apps. Move the PostgreSQL role and source contracts intact; use one versioned shared base role consumed by both repositories rather than independently maintained copies. Choose an existing Ansible collection/dependency mechanism, avoiding a new custom synchroniser.
6. **Move custody metadata, not credential values.** Reconcile exact Bitwarden identities and existing SOPS delivery contracts, preserve ciphertext/versions and escrow, and update only authorised source/destination ownership. Existing passwords, SSH pins, certificates, backup cipher and data remain unchanged. Secret migration is blocked on any ambiguous binding.
   The pinned B2 provider imports application-key metadata without recovering the one-time `application_key` value. Preserve existing BWS/SOPS as backup credential delivery authority and remove dependencies on the transferred key's Terraform secret output before handover; test empty imported output and inverse recovery explicitly. Preserve the existing backup bucket name through an exact operator input rather than transferring the source `random_id` also used by unrelated buckets.
7. **Use NetBird Cloud for routine organisation administration.** Select the managed Free plan, currently covering five users and one hundred machines with access controls, rather than relying on Tailscale's noncommercial Personal plan or operating another management server. Confirm the actual account and plan before enrollment; an existing personal VPN connection does not establish company enrollment identity. Replace the unshipped Tailscale administration role in the shared infrastructure batch, keeping current Tailscale routes available during migration. NetBird becomes the single VPN standard for Q, Exomem, Substrate and the owner phone/workstations/Moshi connections. Separate administrator, server and personal-service peer groups; standardisation does not grant company servers access to personal devices. Allow only explicitly inventoried service ports between those groups. Put the reusable, version-pinned host role and restricted policy in the shared infrastructure repository. Ordinary OpenSSH retains the existing Bitwarden identity and host-key pin; do not enable a provider's separate SSH server or authentication layer. Explicit administrator and server peer groups allow only the intended management port. Inspect and remove the account's default allow-all mesh policy when establishing the restricted company policy, without changing unrelated accounts. Enrollment credentials use exact canonical BWS bindings with secret-free task output. Do not advertise private subnets or exit routes, accept other subnet routes or override host DNS as a side effect. This is an administration transport change, not a database or application traffic cutover.
   Preserve the existing managed SSH commands by deploying the selected mesh address through their canonical profile source. Inventory current phone, workstation, Moshi and server routes first. Verify address/route coexistence during desktop migration, then prove each replacement personal-service and managed-server connection, restart/reconnect recovery and effective DNS settings. Mobile clients switch VPN tunnels for the acceptance pass and retain a working Tailscale fallback; do not assume two VPNs can be simultaneously active on a phone. Retire each Tailscale dependency only after its NetBird replacement passes, removing obsolete routes and credentials through their owning source. Unrelated public application traffic remains unchanged. A successful client `up` command alone is not proof of enrollment, account identity or applied configuration; correlate live peer status with the exact account's API and test real connections. Do not automatically switch an existing foreign enrollment. [NetBird pricing](https://netbird.io/pricing) and [setup-key automation](https://docs.netbird.io/manage/peers/register-machines-using-setup-keys) define the external plan/enrollment contracts; reverify them at implementation.
8. **Prove access before restricting ingress.** Keep the restored narrow public SSH rule during initial adoption. Verify a second managed connection from an authorised administrator device over the tailnet and refusal from an unauthorised device; preserve the host pin and key-only authentication. Only then change provider and guest SSH ingress through their owning IaC to the approved recovery policy. Test boot/service recovery on a disposable host; retain working provider-console recovery. Missing enrollment authority or failed connectivity leaves the current route available and rollout visibly incomplete. Apply the shared pattern to other explicitly inventoried organisation-owned servers in separate governed rollout batches; client systems require their own authority. The approved recovery policy (Hugo, 2026-10-05) admits no public SSH: routine administration uses the company NetBird, and break-glass uses the provider console and rescue system or a temporary operator CIDR applied and reverted through the owning IaC. No home-IP allowlist is retained. Tailscale is not installed on servers and is no server fallback; it remains on owner devices by the operator's 2026-10-04 decision. A newly created host cannot reach NetBird administration until enrolled, so its first convergence uses a temporary CIDR window.
   Replace the base role's current nonempty-public-CIDR assumption with transport-aware validation. Its UFW loop currently only adds rules: the reviewed cutover must explicitly remove obsolete, previously managed public SSH allowances while preserving unrelated rules. Verify effective provider/guest ingress and a new managed connection after restriction; changing the input list alone does not establish closure.

9. **Support simultaneous client and owner work through separate transport instances.** Hugo regularly works on POLLY and his own projects concurrently and requires the same repeatable arrangement on laptop and desktop. Preserve an existing client-owned NetBird daemon and enrollment; switching the active profile does not meet this requirement. A second ordinary kernel daemon is unsuitable: the pinned clients share routing-table and firewall cleanup mechanisms even with different interface names. Use a separately pinned, user-owned Substrate netstack instance where a foreign client already occupies the native daemon. Give it independent state, config, socket, logs and service identity, retain userspace ACL enforcement, and bind its outbound SOCKS listener to loopback only. Disable host DNS, subnet routes and provider SSH integration. Applications use source-managed proxy adapters for outbound connections; this mode does not provide transparent host routing. Incoming service connections are policy-checked before forwarding to loopback at the same port, so bind only the intended local service and retain its existing authentication. Establish the arrangement first with disposable company peers and synthetic local services; verify allowed and denied ports, simultaneous connectivity, restart/stop independence and unchanged host network settings. Then deploy through one shared role on both workstations. Client network configuration and credentials remain outside this programme's authority. Phone and native Windows migration retain their separate transport acceptance requirements.

The named SSH adapter may select an explicitly enrolled loopback SOCKS5 port to reach the company instance. It retains the enrolled destination, account, client identity and sole trusted host key; it accepts no arbitrary proxy command or remote proxy endpoint and never falls back to host routing if that listener is unavailable. Infrastructure owns the VPN; the shared workstation tooling owns this transport adapter.

Workstation SSH uses its existing shared installer with an explicit loopback option. Keep a live legacy listener while adding only 127.0.0.1:2222; without the legacy VPN, install only that loopback listener. Infrastructure owns a one-way owner-device to owner-service TCP2222 grant, with other ports denied. WSL system changes remain operator-applied; subsequent authenticated phone/peer connections establish acceptance.

The company netstack instance uses IPv4 overlay addresses to match that loopback listener; it does not advertise an unsupported IPv6 service path. Converging an existing instance disconnects it, saves the IPv4 setting, then restarts only its user service. The pinned supplier leaves a stale SOCKS listener across down/up, so verify actual outbound SSH after reconnection as well as management connectivity. Native client instances remain unchanged.

The existing Bitwarden peer topology carries the selected workstation endpoints, original verified host keys and optional local SOCKS port. Generic peer wiring opts only that machine's existing key into loopback ingress, requires the enrolled host pin and gives the enrolled transport precedence over ambient SSH defaults. This completes the shared listener and infrastructure policy without duplicating VPN enrollment or replacing SSH identity.

Native mobile clients receive primary DNS through a separate opt-in owner DNS group managed by the shared Terraform source. This enables NetBird's private peer-name resolver; ordinary public queries use the selected upstream resolvers. DNS membership grants no network access. Concurrent WSL clients retain DNS disabled, preserving client-owned resolution. Verify named SSH from the actual phone and retain its old Tailscale entry until that connection passes.

## Migration Plan

1. Complete control SSH acceptance; retain identity/firewall evidence and reconcile the administrator allowlist input. Inventory exact source addresses, consumers, workspace contracts and backup ownership without exposing secrets.
   Resolve the intended tailnet and exact enrollment custody. Deliver and verify the shared administration role on a disposable host, then adopt the control host without closing its current SSH route. The reviewed access policy and profile update must succeed before public-ingress restriction.
2. Create the organisation repository and explicitly safe target workspaces. Install the extracted, pinned modules, host roles, dependency contract and isolated recovery procedure. Keep applies disabled.
3. Prove source forget, target import and inverse recovery on disposable resources using the same provider versions. Prove an isolated restore of the latest selected production backup without exposing it to production applications or external effects.
4. Freeze both source writers and target writers, including the durability domain and Ansible/control-node configuration. Retain private remote-state version IDs and the exact provider manifest. Prepare both saved plans and review their state-only actions; reverify live identities immediately before each state mutation.
5. Apply source forget and target adoption through their exact workspace guards, one domain at a time. Retain durable checkpoints between steps. Keep all writers frozen during any ownership gap; complete target adoption or recover source ownership without provider mutations.
6. Deliver Exomem dependency integration and retire the transferred management code and old control-node targeting while the writer freeze remains active. Keep declarative removal evidence and one canonical recovery/source owner. Verify the actual merged delivery revisions cannot recreate or configure the transferred host.
7. Verify target states own every selected ID once and source states own none. Verify ordinary plans from the actual delivery revisions have no unapproved changes, DNS/IP/network identity, key-only managed tailnet SSH, TLS database health/role boundaries, backup/WAL continuity and representative Substrate/Exomem consumers. Lift the freeze only after source retirement, dependency publication and these receipts. Move completed shared contracts into the target's OpenSpec during coordinated specification closure.

**Rollback:** Freeze both writers. If target owns an adopted resource, forget it there with `destroy=false` before restoring its original source management by reviewed import; never restore an old source state while target still owns the same ID. Revalidate resource manifests, ordinary no-change plans and consumers before releasing the freeze. No rollback deletes a provider resource or restores database content.

## Risks / Trade-offs

- Partial state handover → checkpoints and continued writer freeze; recovery changes management only.
- Shared network still owned by Exomem → explicit dependency/protection remains; broader network ownership transfer is a separate design.
- Role or secret-contract duplication → one pinned source/dependency for shared base configuration and exact custody reconciliation.
- Provider import defaults cause drift → disposable reproduction and exact saved plans; reject unexpected mutations rather than accepting them.
- Backup extraction weakens recovery → preserve separate durability state, retention, cipher and off-host lineage; isolated restoration is a pre-handover gate.
- A broad or wrong mesh enrollment widens access → explicit account identity, server peer groups, permission tests and no subnet advertisement; preserve BWS SSH authentication as a second boundary.
- Concurrent VPN clients can conflict in address selection, routes or DNS → retain Tailscale during staged migration, verify desktop coexistence and mobile tunnel switching, then retire dependencies only after replacement workflows pass.
- A VPN outage locks out operators → verify boot recovery and provider-console access, stage ingress restrictions after a second successful managed connection.
