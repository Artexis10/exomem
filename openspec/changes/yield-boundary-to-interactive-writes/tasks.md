## 4. Closure

- [ ] 4.0 A rehearsal of a large import (a stage of about 69,300 notes in pages of 5,000) files every page with no livelock and no refused writer. It passes when: (a) no call is refused 30 times and the planning calls of a page after the first move their cursor; (b) no writer, the cell's filer included, is refused with `holder_overdue` or `capture_wait_exhausted` (the report counts the agent's refused calls by cause, and reads a filer row of the mutation journal, `scope` owner, as one of the two); and (c) the report counts the refused writes (`paging_refusals`) by cause and the journal's `MUTATION_BUSY` rows by command, and gives the seconds of every page (`file_seconds_by_page`), the rate of each page and the projection of the whole import (`file_projection`, from the per-page rate, with the seconds left to the deadline), all of it also when the deadline ends the paging. The report names the runner's machine (vendor, CPU model, root disk) and the CPU of the `start` call, which scales each page's seconds beside the raw ones (`page_file_seconds_per_start_calibration`), because the runner's zlib calibration did not follow the cell's CPU between two machine classes. At that size the scan (19.9 s for `start` in run 45941473643) and the warm walk (about 6 s projected) are inside the 30 s limit, so a refusal comes from a chunk, a `plan` call or the code after an item loop, and fails (b). No baseline exists: `main`'s last large import (run 45890946426, at `04a1e1bc2`) failed straight after the upload, before paging, so it never reached a page to compare. Missing the run's 115-minute deadline (counted from its start) does not fail 4.0: it is the throughput residual of the follow-up change (the per-item cost of the plan, the prework and the commit, and the resumable overview), unless the time per page grows from this change's own mechanisms. Per-call means of the spans do not show that, because a call is capped to the hold's room; the per-item milliseconds do (commit, plan and prework by page, in design.md), and so does a `file` call of the filer on a stage that an agent files, which the filer's standing aside removes. At 10.0 files per second the import needs about 6,900 s against about 5,650 s left of the deadline, so the deadline is expected to be missed until the follow-up ships. The filer stands aside from the stage that the scripted agent files, so this run files with one importer: it proves that importer and the filer's yielding at size, not the fix of the livelock between two importers, which rests on run 45941473643 (four pages in strict alternation, no livelock) and on task 3.4.
