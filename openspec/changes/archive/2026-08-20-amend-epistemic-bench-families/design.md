# Design — amend-epistemic-bench-families

## Context

The epistemic-state pre-registration (`benchmarks/epistemic/PREREGISTRATION.md`) is founder-ratified: `contracts/ratification.v1.json` records `decision: ratified, ratified_on: 2026-08-11`, and `protocol/contracts.py` pins both the contract sha (`21aa5a88…`) and the receipt sha, with the run-manifest schema requiring the ratification block. The working file is byte-identical to the ratified sha — including its now-historical "Status: PROPOSED" header, which froze inside the ratified bytes and which no check flags. The 2026-08-14 epistemic audit identified five uncovered loop-closure families and mandated contracts-first sequencing: these measurement contracts precede the Tier-1 implementation (`add-epistemic-loop-primitives`) that they will measure.

## Goals / Non-Goals

**Goals:**
- f15–f19 exist as ratifiable §7 Amendment entries with deterministic assertions and acceptance predicates in the registry's existing style.
- Post-ratification amendment governance is mechanical: a receipt shape, chain validation, manifest lineage, and a drift check that names stale or silently-edited pre-registration state.
- The stale Status header is corrected through the same governed path it violates today.

**Non-Goals:**
- No family driver, fixture, or corpus (follow-up changes own those). The six §2 assertion *callables* are in scope after all — see Decision 9: registering f15–f19 is what turns the §1/§2 drift tests green honestly, and a registered name with no implementation would move "unknown assertion = load error" from load time to run time.
- No change to f01–f14, the catastrophic set's existing members, the G1–G5 gates, or any run semantics for existing families.
- No product runtime, MCP surface, or model use.

## Decisions

1. **§7 Amendments, not file replacement.** The freeze contract prescribes exactly this path for post-ratification change; the pinned base sha remains the ratified identity and amendments extend it. Alternative (re-ratify a v2 file wholesale) rejected: it would orphan the pinned constants and the existing receipt, and would erase the amendment history the freeze exists to preserve.
2. **Amendment receipt mirrors `ratification.v1.json`.** `preregistration-amendment-receipt.v1` carries: base contract sha, amended file sha, amendment date, reason, founder acknowledgment (ratifier + date). Symmetry keeps the validation code one shape family and the founder ceremony identical. Alternative (a single append-only amendment ledger file) rejected: per-amendment receipts match the existing one-artifact-one-receipt pattern and keep each acknowledgment independently verifiable.
3. **Drift-check semantics.** The working file MUST be byte-identical to the ratified base sha, OR equal to the base evolved through a receipted amendment chain (fold: each receipt's `amended_sha256` must equal the file hash after its amendment; the last receipt's hash must equal the current file). Any other state is a named failure. This is what would have caught the stale header the day it mattered.
4. **f18 catastrophic-set candidacy is adjudicated in the amendment text, decided at acknowledgment.** The amendment proposes `negative_result_retention`'s core assertion for the catastrophic set (silently losing a refuted result mirrors `prior_revision_retained`); the founder accepts or strikes it when acknowledging — governance stays with the ratifier, not the author.
5. **Families may describe not-yet-shipped canonical Markdown.** f15/f18 reference prediction units and verdict metadata that Tier-1 will introduce. The pre-registration's own rules already handle this honestly: capability-declared `not_applicable` excludes a family from comparative claims for all providers, and the claim-conditioned rule turns absence into `fail` only where a product's own materials claim the property. Exomem will claim it only once Tier-1 ships — which is the contracts-first point.
6. **Status-header correction rides the first amendment.** The header edit is a content change to frozen bytes, so it must itself be a receipted amendment; folding it into the f15–f19 amendment avoids a ceremony-only receipt.

7. **A pending acknowledgment withholds the amended families, not the repository.** The first implementation raised the typed pending refusal inside `fold_amendment_chain` and inside identity derivation. Both are *identity* paths, so one unacknowledged receipt refused every consumer that loads the pre-registration at all — `start_manifest` wrapped it as `ManifestError: pre-registration identity refused`, and all eight CI shards went red, including runner-lifecycle and provider-state tests with no connection to benchmark comparison. That is not what the receipt claims. Its own `effective_policy` reads "until then f15-f19 cannot support comparative runs or claims", and that is the correct scope. The refusal is therefore re-aimed: the chain folds and the identity derives while an amendment is pending, `AmendmentIdentity` records `acknowledgment_status` and the `introduced_family_ids` it derives by differencing its §1 table against its parent's, and `require_amended_families_released` refuses exactly the runs, scores and claims that name a withheld family. The fail-closed guarantee is unchanged in force and narrower in aim.

   Alternative rejected — leave the refusal broad and simply acknowledge sooner: that is the deadlock in Decision 8, not a way out of it. Alternative rejected — drop the refusal entirely and rely on the frozen registry (f15–f19 are not yet in `PREREGISTERED_FAMILY_IDS`, so a scenario naming them fails to load today): that is an accident of sequencing, not a governed gate, and it evaporates the moment the follow-up change adds the families to the registry.

8. **`repository_revision` is recorded in a follow-up on `main`, after the squash merge.** The receipt requires its named revision to be a Git ancestor of the run pin (`git merge-base --is-ancestor`, `_git_applicable`). This repository is squash-merge only, so every branch commit sha is orphaned at merge: a revision pinned before merge cannot be an ancestor of anything on `main`. This is not hypothetical — the first acknowledgment attempt pinned `382d01c9`, a pre-rebase sha that is already not an ancestor of the branch head. The ratification receipt's `7cd15e6d…` is durable precisely because it was recorded *after* that work landed. So while a receipt is pending, derivation takes the amended-document revision from the receipt's uniquely reconstructed introduction commit — a real commit that carries the amended bytes and satisfies every ancestry and digest binding — and the founder records the durable `repository_revision` on `main` afterwards.

   Consequence for restoring a pending state: the acknowledgment must be *dropped from history*, not reverted forward. A revert commit gives the receipt path three history events, and the receipt-tamper rule allows exactly one pending→acknowledged transition, so derivation refuses with "receipt changed outside the single allowed pending-to-acknowledged transition". Verified empirically before choosing the restore method.

9. **Registration is not release, and the two must move together.** The §1/§2 drift tests compare the code registry against the amended document, so they were red from the moment the amendment landed: 14 families and 18 assertions in code against 19 and 24 in the file. The honest fix is to register f15–f19 and their six assertions rather than edit the expectations down. But registering them *alone* would have been strictly worse than leaving the tests red: the scenario loader refused f15–f19 only because §1 did not know the ids, and that incidental protection disappears the moment they are known — while the declarative manifest gate stayed latent, because nothing threaded scenario families into `start_manifest`. The net effect would have been that an **unacknowledged** amendment's families became runnable, which is the precise failure this change exists to prevent.

   So both halves land together. `AMENDMENT_INTRODUCED_FAMILIES` mirrors §7 in code (drift-tested against the Git-derived receipt chain), `epistemic.amendments` answers "is this family released?" from the working receipt bytes alone, and the refusal is wired into every surface that can run, score, or record a family: the scenario loader, `evaluate_scenario`, `assemble_family`, `start_epistemic_manifest`, and `load_epistemic_manifest`. The loader is the choke point that makes it unbypassable — nothing downstream can obtain a `Scenario` for a withheld family — and the others are defence in depth for objects built without it.

   The acknowledgment check deliberately reads *receipt bytes*, not Git history. Reconstructing the pinned identity needs `git log`, and making an ordinary fixture load depend on that would break scenario loading in any checkout without history. Unreadable receipts fail closed: every amendment-introduced family is withheld.

## Risks / Trade-offs

- **Chain complexity vs one receipt:** the fold validation is a few lines and buys tamper-evidence; accepted.
- **Aggregate suppression blast radius** if f18 joins the catastrophic set: a product silently dropping refuted results suppresses all its aggregates. That is the intended severity, but it is the founder's call (Decision 4).
- **Schema movement:** the run-manifest schema gains an optional amendment-lineage block; consumers pinned to v2 must tolerate its absence (additive, defaulting to base-only lineage).
- **Two sources of family truth during the gap** (amendment accepted, fixtures not yet built): mitigated by the existing "unknown assertion name = fixture load error" rule — nothing can silently run a family the runner does not implement.
- ~~**The withheld-family gate is declarative**: `start_manifest`/`load_manifest` refuse only the families a caller *declares*, so the gate is latent until a runner threads them through.~~ **Closed by Decision 9.** `epistemic.manifest` derives the family set from the scenarios a run executes and passes it to both, and three further surfaces (loader, evaluator, scorer) refuse a withheld family without needing a caller to declare anything. What remains uncovered is calling an assertion callable directly — `resolve("refuted_retrievable_at_full_standing")(ctx)` — which produces an `AssertionResult` in memory and is neither a run, a score, a manifest, nor a claim. The discrimination tests do exactly that, deliberately.
- **The cohort/report path is not family-keyed.** `ValidatedEpistemicCohort` rows carry provider, variant and assertion cells, with no `family_id`, so there is nothing there for a family gate to check. A hand-authored cohort naming an amended assertion is a *forged artifact* problem, addressed by the evidence-ref and replay machinery, and is equally available for the eighteen ratified assertions — not a regression and not a hole this change opens.
- **Deriving introduced families from the §1 table** couples identity derivation to the contract document's Markdown shape. Bounded deliberately: a document with no §1 section declares no families (so an amendment that introduces the table has every row counted as introduced — fail-closed), while a §1 section that exists but parses to nothing refuses rather than silently releasing families.
