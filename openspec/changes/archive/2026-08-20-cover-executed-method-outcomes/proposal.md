## Why

A conversation reached a complete, reproducible, explicitly successful result and nothing was captured until the user asked "did you save that?". That is a direct failure of the shipped no-nudge product test: when ordinary conversation already establishes a durable reusable result, requiring an explicit save is an ergonomics failure.

The obvious diagnosis is wrong, and checking it first is what makes this change small. The surface was ChatGPT, which is in `HOOKLESS_SURFACES` and so runs at `maximal` prominence, and the user's client did carry the documented custom-instructions block. Delivery was in place. The re-armer was in place. The agent simply followed instructions that do not cover the case.

Every carrier enumerates the same closed list. `prominence.py` maximal: "a decision, a resolved problem, a diagnosed failure, a reusable pattern, a fact about a recurring entity". The scaffold: "a durable conclusion lands or a durable recurring entity accumulates reusable facts". The copy-paste block: the same five, plus person/project/organisation.

A method someone actually carried out and reported the result of is none of them. It is not a decision, nothing was broken so it is not a solved problem, it did not fail so it is not a diagnosed failure, it is not a `Patterns` page, and it is not a fact about a recurring entity. The list is knowledge-work shaped, and every hands-on domain falls through it — cooking, training, maintenance, any physical or procedural experiment. The bar was already "low"; the class was simply absent.

## What Changes

- Name the missing class in the stepping-stone predicate on every carrier: a concrete method was executed, the user reports the result, the result is clearly good, bad, or diagnostically informative, and the method or lesson is reusable later.
- State the routing so the class does not collapse into one page type: a proven method to its own page, a parameter comparison to an experiment, a diagnosed failure mode to a failure note, and nothing reusable stays unwritten.
- Say explicitly that being asked afterwards is the failure, not the trigger. The existing text says what to capture but never that waiting to be asked is itself the defect.
- Apply it to all four carriers, because they reach different clients: the bootstrap payload (the entire contract a hosted or generic MCP client ever sees), the prominence contract at both `balanced` and `maximal`, the scaffold skill, and the hand-pasted custom-instructions blocks that are the only lever on a web client.

## Capabilities

### Modified Capabilities

- `agent-bootstrap-contract`: the capture predicate covers an executed method whose outcome the user reports, with routing by what the outcome yielded, on every carrier that teaches capture.

## Impact

The bootstrap epistemic contract, both prominence capture strings, the scaffold skill's stepping-stone block and implicit-routing table, the documented copy-paste blocks, and the regenerated Claude plugin skill copies. No MCP tool, description, parameter, or input schema changes, so the packaged tool-surface fingerprint is untouched. The compact payload grows 652 bytes against 1,723 of headroom, and the maximal copy-paste block goes from 1,137 to 1,264 characters against its stated ~1,500 cap.

Deliberately out of scope: any new detector, sensor, or server-side signal. Nothing was written in the failing conversation and no Exomem tool was called at all, so no substrate carrier — including the deferred due-state work — could have reached it. On a hookless surface with no tool call, contract text is the only lever, and this change should not be read as implying otherwise. Also out of scope: hook changes, prominence level defaults, and the AT-1 bench item that would make this falsifiable, which belongs to a sequence-3 amendment alongside the calibration constants already awaiting the founder study.
