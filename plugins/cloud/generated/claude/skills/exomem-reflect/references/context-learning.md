# Learn from a context miss

Use this workflow when an observed miss or source-backed feedback calls a durable conclusion or its delivery into question.
Make the source-backed correction whenever the feedback supports one and the active engagement policy permits the write. File the miss in an incident collection only when the user asks, a workflow engages this procedure, or the live engagement policy delegates filing observed outcomes.
For new material, first use the existing capture and compilation workflow in [writing](writing.md).
Use this procedure when that material supports a correction or exposes a context failure.
The active agent diagnoses and writes through existing tools. This procedure adds no background learner or automatic correction.

Read [writing](writing.md), [Planning and Records](planning-records.md), and [mutation results](mutation-results.md) before their corresponding writes.
Use the current capability list and engagement envelope. A miss, advisory, or example grants no additional authority.

## Preserve the observation

1. Reuse the incident and source references already held in context; the observation keeps its existing identity.
2. Inspect the selected incident collection's manifest; its fields, natural key, and lifecycle remain authoritative.
3. Link the observed request, available context, source-backed expectation, and missing evidence; unsupported details stay explicit gaps.
4. Preserve original material through its permitted capture route; the returned source or evidence reference establishes provenance.

Reuse an existing incident collection when its declared schema fits.
Map evidence roles to that schema instead of adding a product taxonomy or a parallel queue.
The roles are the source-backed expectation, the context that reached the agent, committed correction evidence, retrieval and later-answer checks, and unresolved evidence or behavior.
A vault built from the scaffold carries an optional example collection at `_Schema/examples/context-learning/incident-collection.md`; it does not authorize collection creation.

Keep the record bounded and within the source's disclosure rules.
Do not copy transcripts, private artifacts, or withheld content into a more visible incident.
If the original delivered context is missing, record that gap. The first failed boundary remains unknown.

## Locate the first supported failure

Compare the source with the stored knowledge, catalogue description, discovery results, delivered context, and answer.
These are reasoning questions, not lifecycle values to add to a collection.
A generated answer, retrieval rank, or naming counter cannot establish source truth.

If the source is unavailable, preserve the evidence gap.
If the source and supplied context are correct, investigate the engine or answer behavior without rewriting correct facts.
If an authored constraint is absent from the description, consider a supported summary correction with its source and target version.
Resolve aliases, topics, and relations through their existing registries and ambiguity rules.

## Apply one supported correction

1. Read the current target and its provenance; the proposed change cites the source and current target version.
2. Select the existing governed writer; the live envelope determines whether this action can proceed.
3. Submit the supported correction with the writer's current guards; immutable Sources and Evidence remain intact.
4. Inspect the terminal mutation result; the incident links the actual receipt and resulting target reference.

Use `edit_note` for a guarded correction and `supersede_note` when the existing supersession contract fits.
Use supported summary, topic, alias, and relation writes when their evidence and registry resolution support the change.
A multi-step curation plan retains its own preview and apply authority.

If the target changed, reread it and reconsider the correction.
For an uncertain acknowledgement, preserve the same mutation identity and unchanged payload, following [mutation results](mutation-results.md).
A refused or unresolved mutation is not a committed correction. Never invent a receipt reference.

## Check retrieval and ordinary use

1. Retrieve the corrected material through the supported read route; record the actual returned version and result.
2. Recheck the exposed miss under the declared conditions; retain failures alongside successful writes.
3. Freeze a fresh source-derived expectation through an independent key writer; the answer actor receives no truth key.
4. Check the fresh ordinary answer and an unrelated-topic control; record what improved, failed, or remains unavailable.

Use the exposed miss for diagnosis and repair verification.
Report the fresh check separately when judging transfer beyond that example.
Change one hypothesis between development rounds and use the smallest check that answers it.
Reuse valid boundary evidence before adding another test or run.

Held-out evaluation inputs, truth keys, arm maps, and generated held-out answers never supply corrections or examples.
Record their exclusion without restating their contents in a prompt, incident, or fixture.
Do not run an optional check without its required capacity, evidence, and authority.

## State the verified outcome

Keep committed data, successful retrieval, and useful downstream answers distinct in the incident's declared fields and evidence links.
These distinctions do not require new field names or lifecycle values.
When the manifest does not define what a lifecycle value means, choose the value that does not overstate the check, and name the check you performed.
A successful write alone cannot close a miss; a failed later answer remains visible.
An unavailable check stays unresolved while ordinary recall remains available.

For a measured improvement, name the cases, target versions, instrument, failures, and case-level comparison with uncertainty.
An interval that includes zero means no change.
Report a supported local repair at its actual scope; do not claim a default switch or general quality gain from it.

Bulk repair, model backfill, and unattended learning keep their existing authority and default-off state.
This workflow adds no server model call, scheduler, or semantic classifier.
