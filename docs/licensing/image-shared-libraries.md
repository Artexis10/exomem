# Shared libraries in the published images

This record lists the shared libraries in every published container image (`lean`, `ml`, `cuda`, `cloud` and `cellctl`) with the licence of each. It is the scan record that OpenSpec change `adopt-fair-source-licence` requires. The generator is `scripts/image-library-inventory.py`. Do not edit this file by hand: change the inputs and regenerate it (last section).

The requirements that this record serves:

- No third-party strong copyleft in code that the product imports or links. LGPL libraries may ship as separate, replaceable shared objects.
- Licence choices and linking exceptions are recorded.
- The operating-system layer is recorded in its own part and is not treated as combined with the product.

Every count in this file comes from the collected records. No count is typed by hand.

## Status: the first FSL release

This record covers the published images of the first releases under FSL-1.1-ALv2. The `lean`, `ml` and `cuda` images come from v0.202.0, the first FSL release. v0.202.0 published no `cloud` or `cellctl` image, because its arm64 licence check could not scan the arm64 image, so those two images come from v0.203.0, the first release that published them. Every platform that each release published is scanned.

Unmapped and Strong copyleft are 0 in every row. OpenSpec task 3.4 of `adopt-fair-source-licence` required this before the release statement.

## How to read this record

Each scanned image has three parts.

- Part A lists the shared libraries that Python wheels bundle (`*.libs/` directories and vendored `.so` files). No off-the-shelf scanner reports their licences. The generator finds them in the image layers and maps each to its upstream project and licence in `scripts/image-licences/library-upstreams.yaml`. An unmapped library shows as `UNMAPPED` and counts in the Unmapped column, so a new bundled library cannot enter an image unrecorded.
- Part B lists shared libraries that neither a package manager nor a wheel owns.
- Part C lists the operating-system layer: the dpkg packages of the Debian base, in two groups. System libraries are dpkg section `libs`. Programs and data are every other section. The operating system is aggregated with the product in one image. The product does not combine with it.

The Evidence column of Part A names the licence file that the wheel ships and that states the library's licence. `none shipped` means that no file in the wheel's `.dist-info` directory, and none at the top of a package directory that its RECORD lists, states that library's licence. The licence is then the upstream project's published licence, taken from `scripts/image-licences/library-upstreams.yaml`, and it is not checked against the binary. Where a licence is offered as a choice, the table names the licence elected. Elections for whole Python distributions live in `scripts/image-licences/elections.yaml`.

Classes:

| Class | Meaning |
| --- | --- |
| permissive | BSD, MIT, Apache-2.0, ISC, Zlib and similar. |
| weak-copyleft | LGPL, which the library ships as its own shared object that a user can replace. |
| linking-exception | GPL with the GCC Runtime Library Exception 3.1. The exception lets any program link the library. |
| strong-copyleft | GPL or AGPL, which the product cannot import or link. |
| proprietary | Vendor licence, recorded as the wheel declares it. |

In Part C the class is the one that trivy assigns from the lists in `scripts/image-licences/trivy.yaml`: `forbidden` is GPL and AGPL, `restricted` is LGPL, `unknown` is a licence on neither list, and a package with no licence read says `none read`. A Debian copyright file lists the licence of every file in the source package, packaging files included. A `forbidden` entry in Part C therefore marks a package to read. It does not show that the product links the library.

## How the product uses the operating-system layer

- The product starts these programs as separate processes with an argument list, and it never imports or links them: `tesseract` (OCR), `age` and `age-keygen` (encryption), and `restic` (backup). The `cloud` image installs them.
- The image holds no `ffmpeg` command. PyAV decodes audio and video through FFmpeg shared libraries. The `cloud` image builds those from the FFmpeg source release with no `--enable-gpl`, `--enable-version3` or `--enable-nonfree`. They stay separate files in `/opt/ffmpeg-lgpl/lib`, and Part B lists them.
- CPython links system libraries, such as the C library. Three CPython standard-library modules link GPL or other copyleft libraries: `readline` (libreadline, GPL-3.0-or-later), `_gdbm` (libgdbm, GPL-3.0-or-later) and `_dbm` (Berkeley DB, Sleepycat). The product does not import them. Regeneration step 8 checks this: it imports every module of the `exomem` package and reports which of the three loaded.
- The GCC runtime libraries (`libgcc_s`, `libstdc++`, `libgomp`, `libatomic`) carry the GCC Runtime Library Exception 3.1.
- Trivy reads no licence for some Debian packages, because their copyright file states the licence as free text. Part C shows `none read` for each. For the packages that `scripts/image-licences/library-upstreams.yaml` lists, it also shows the licence and the copyright file in the image that states it, such as `/usr/share/doc/gcc-14-base/copyright` for the GCC exception text. Regeneration step 9 reads the copyright files of the other system libraries and checks that none names a GPL or LGPL licence.

## What this record does not cover

- Every record is a released image. Each record names its release in the Source column. The image build context (`Dockerfile`, `uv.lock` and `infra/cellctl`) differs between v0.202.0 and v0.203.0 only in the version number, so the two releases describe one dependency set.
- Each record covers one platform. The `cuda` image publishes `linux/amd64` only.
- Static linkage inside a compiled module is not visible. For example, a PDFium or PyTorch binary can contain code from other projects. The wheel's own licence files are the evidence for those, and Part A lists them by count.
- The scan reads files, not the dynamic linker. It does not follow `DT_NEEDED` entries to show which library each module loads.

## Regeneration

1. Install the pinned `trivy` with `RUNNER_TEMP="$(mktemp -d)" scripts/ci-install-trivy.sh`, and put `$RUNNER_TEMP/trivy` on `PATH`.
2. Install `oras` at the release that `infra/tool-versions.env` pins, or later.
3. For a released image, run the `Regenerate` command from its section, with `CACHE` set to an empty directory and `RECORD.json` set to a path in one records directory.
4. For a tree image, check out the commit that the section names. Run `docker build --target TARGET .` with the target in the section's tag, then `docker save -o IMAGE.tar IMAGE`.
5. Run the section's `Regenerate` command with `IMAGE.tar`.
6. Run `uv run --frozen python scripts/image-library-inventory.py render RECORDS --upstreams scripts/image-licences/library-upstreams.yaml --header scripts/image-licences/library-record-header.md > docs/licensing/image-shared-libraries.md`.

The expected result is a record file with the `UNMAPPED` count at zero in every row of the Counts table. Add the missing entry to `scripts/image-licences/library-upstreams.yaml` for each library that shows as `UNMAPPED`, and render again.

Steps 7 to 9 are manual checks that the generator does not run. Run them in the `cloud` image, which has the most system libraries, and run step 8 also in the `ml` image, which carries the torch stack. The `cuda` image has the same Python packages as `ml`, with the CUDA build of torch and the NVIDIA wheels, and is not probed.

7. Save the import probe below as `probe.py`.

   ```python
   import importlib, pkgutil, sys
   import exomem

   for module in pkgutil.walk_packages(exomem.__path__, "exomem."):
       try:
           importlib.import_module(module.name)
       except Exception as error:  # a module whose extra the image lacks cannot import
           print("not imported:", module.name, type(error).__name__)
   print("loaded:", [m for m in ("readline", "_gdbm", "_dbm") if m in sys.modules])
   ```

8. Run `docker run --rm -i --entrypoint python IMAGE - < probe.py`. The last line must read `loaded: []`.
9. For each system library that Part C shows as plain `none read`, run `docker run --rm --entrypoint cat IMAGE /usr/share/doc/PACKAGE/copyright | grep -i gpl`. It must print nothing.

Results on 2026-11-25, in the images of `cloud-v0.203.0-amd64` and `ml-v0.202.0-amd64`: step 8 printed `loaded: []` in both, and it listed four `exomem.tui` modules that did not import because the image lacks their extra. Step 9 printed nothing for `libfontconfig1`, `libxau6`, `libxdmcp6` and `libxrender1`. Replace this paragraph when you run the steps again.
